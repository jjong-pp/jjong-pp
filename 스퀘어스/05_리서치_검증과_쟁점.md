## 2. 04의 "빈칸 3개"가 무너졌다 — 가장 중요한 절

04 5-1절은 경쟁 제품이 안 하는 빈칸 3개를 찾았고, 그걸 근거로 **F2의 정의를 다시 쓰라**고 했다. 그 빈칸을 재검증했다.

| 04가 주장한 빈칸 | 검증 결과 |
|---|---|
| 출처의 통제 가능/불가 분류 | ⚠️ Profound가 인용 URL별 아웃리치·Knowledge Base 수정·콘텐츠 생성 행동을 제공한다. 다만 공개 문서에서는 통제 수준과 실행 권한을 명시적 필드로 분류하는지 확인되지 않음 |
| 사실 오류 검출 + 수정 후 재측정 순환 | ⚠️ Profound FactCheck가 오류 검출·관련 인용 URL·대응 Agent·기간별 정확도 비교까지 제공한다. 다만 특정 행동의 기준선·측정 버전과 이후 결과를 직접 연결하는지는 확인되지 않음 |
| 측정 예산 배분 근거 | ✅ 여전히 미확인. 모델·언어·패러프레이즈·반복의 예산 효율을 공개 연구에 따라 배분한다고 밝힌 제품은 찾지 못함 |

### 2-1. 사실 오류 검출과 대응은 이미 상용화됐다

| 제품 | 하는 일 |
|---|---|
| **Profound FactCheck** | 객관적·원자적 브랜드 주장을 고객 Knowledge Base와 대조하고 `accurate / inaccurate / not relevant`로 분류한다. 부정확한 주장에 관련 인용 URL을 연결하고, 대응 Agent와 기간별 Accuracy Score·Share를 제공한다 |
| **Waikay** | 브랜드에 대한 가격·기능·위치·팀 정보의 사실 정확성을 모델·주제별로 수집하고 사용자가 정확/부정확을 확인하도록 지원한다 |
| **FactSentry** | 브랜드 환각 탐지·수정. ChatGPT·Perplexity 24시간 모니터링 |
| **Ryze AI** | LLM의 브랜드 서술 모니터링, 환각·사실 오류 탐지, **출처에서 수정** |
| **Scrunch AI** | 콘텐츠 갭 식별 + **오정보 탐지.** 헬스케어·금융 등 규제 산업 대상 |

**Profound FactCheck는 초안의 FR-13·FR-14와 직접 겹치고 대응 Agent·기간 비교까지 제공한다.** 따라서 사실 오류 탐지 자체는 차별화 근거로 쓰지 않는다. 다만 고객 영향에 따른 P0 확정, 사용자가 선택한 행동의 기준선·질문/산식 버전 저장, 동일 조건 재측정 후 `개선/유지/악화/비교 불가` 판정은 공개 문서에서 확인되지 않았으므로 제품 설계 가설로 남길 수 있다.

### 2-2. 확정한 처리 방식

- 과제 본문은 경쟁 우위 피치가 아니라 시나리오 고객의 문제와 두 기능에 집중한다.
- 다만 우선순위 근거에서 Profound FactCheck와 기능 중복을 숨기지 않고, 오류 탐지 자체를 차별화로 주장하지 않는다.
- 차이는 `고객 문제에서 목표 질문 생성 → 고객 영향으로 우선순위화 → 사용자 확인 → 선택한 행동과 동조건 재측정 연결`이라는 제품 가설로 제한한다.
- 경쟁 제품에 이 구조가 없다고 단정하지 않고, **검토한 공개 문서에서 직접 확인되지 않았다**고 표현한다.

## 3. 기준 3이 정면으로 맞는 반증 — Bain

### 3-1. 숫자

> **무브랜드 프롬프트(특정 브랜드를 지목하지 않은 질문)의 89%가 서드파티 출처로 채워진다.**
> Bain, Scrunch AI 검색 데이터 약 **5억 건 인용** 분석. 주제별 분산 76~99%.
> 자사 홈페이지·블로그·유료 광고가 아니라 리뷰 사이트·업계 매체·애널리스트·소셜·제휴 콘텐츠가 지배한다.

### 3-2. 이게 왜 문제인가

기준 3의 현재 문장은 이렇다.

> "답변이 브랜드를 언급하며 참조하는 출처 중, **자사가 직접 수정·갱신할 수 있는 자산의 비중이 높은 상태**입니다." (`01` 69행)

그리고 지표를 **"통제 가능 출처 비중"** 으로 잡았다 (`01` 87행).

**Bain이 맞다면 이 지표는 구조적으로 도달 불가능한 목표를 세운 것이 된다.** 시나리오의 질의는 대부분 "협업툴 추천해줘" 같은 무브랜드 질의이고, 거기서 자사 도메인 비중은 원래 낮다. 고객이 이 지표를 "개선"하려면 무엇을 해야 하나 — 답이 없다.

**게다가 이건 면접에서 나올 확률이 높은 질문이다.** 회사가 GEO 제품을 만드는 중이면 이 숫자를 이미 알고 있을 가능성이 크다.

### 3-3. 그런데 뒤집을 수 있다

같은 숫자가 **기준 3을 죽이지 않고 오히려 근거가 되는 읽는 법**이 있다.

| | 지금 (비중 최대화) | 대안 (경로 판별) |
|---|---|---|
| 기준 문장 | 통제 가능 출처 **비중이 높은** 상태 | 우리를 말하게 만드는 출처가 무엇이고, **그중 손댈 수 있는 경로를 알고 있는** 상태 |
| 지표 | 통제 가능 출처 비중 ↑ | 출처 구성 + **대응 경로가 지정된 출처 비중** |
| Bain 89% | **반증** | **근거** — "자사 사이트만 고쳐서는 안 움직인다"는 증거 |
| 개선 행동 | 자사 문서 수정 | 리뷰 플랫폼 갱신 요청 · 업계 매체 대응 · 대체 콘텐츠 유통 |

> **이 전환의 값:** 기준 3의 원래 목적은 "고칠 수 있는 지표를 만든다"였다(`01` 71행). 비중 최대화는 그 목적을 **오히려 배신한다** — 도달 못 할 목표라서. 경로 판별로 바꾸면 목적이 살아난다. **그리고 Princeton의 "Cite Sources 기법이 5위 페이지를 115% 올린다"가 여기에 정확히 붙는다** — 남의 출처를 인용하는 것이 레버라는 뜻이므로.

**결정 완료:** 통제 가능 출처의 비중을 높이는 대신, 출처의 정확성·최신성과 가능한 대응 경로를 구분한다. 이 판단은 결정 07과 최종 기준 3에 반영했다.

## 5. 검토 후 제외 — 이번 제출의 이중언어 실험

아래 비교안은 리서치 단계에서 검토한 대안이다. 그러나 2607.13304의 결과변수가 노출·추천이 아닌 다국어 감성값이고, 1차 사용자를 한국어 기반 국내 B2B SaaS 담당자로 확정했으므로 결정 21에서 **한국어 집중안**을 선택했다. 언어 차이는 후속 확장 가설로 남기고 이번 제출의 27회 파일럿에는 넣지 않는다.

### 5-1. 현행 vs 논문 반영

| | `03` 현행(최소) | 논문 반영안 |
|---|---|---|
| 질의 | 12 | 3~4 |
| 모델 | 3 | **4** (ChatGPT·Claude·Gemini·Perplexity) |
| **언어** | **없음 (한국어만)** | **2 (한국어·영어)** |
| 반복 | 3 | 3 |
| 총 실행 | 108 | **72~96** |
| 나오는 발견 | 회차 간 편차 | 회차 간 편차 **+ 언어 간 편차 + 모델 간 편차** |

### 5-2. 당시 기대했던 장점과 현재 판단

1. 이중언어 비교는 후속 확장 시 유용한 탐색 실험이 될 수 있다.
2. 그러나 해당 논문의 31.6%는 특정 모델 스펙의 감성 결과이므로 국내 협업툴 추천률에 그대로 적용할 수 없다.
3. 이번 제출에서는 한국어 질문의 추천 역할·사실 정확성을 사람이 검수하는 것이 고객 문제에 더 가깝다.
4. 따라서 `3개 한국어 질문 × 3개 환경 × 3회 = 27회`를 권장 파일럿으로 확정했다.

### 5-3. 후속 확장 시 최소 탐색안

제품이 다국어 고객으로 확장될 때 최우선 한국어 질문 하나와 의미·지역 조건이 같은 영어 대응문을 만들어 3개 환경×3회로 비교한다. 결과는 한 질문의 탐색 표본으로만 해석하고 시장 전체로 일반화하지 않는다.

## 6. 해결됨 — 혼합 측정 정본

사용자는 **API 공식 시계열 + 개인화 요인을 줄인 웹 UI 표본 점검**의 혼합형을 선택했다. 여기서 혼합은 두 숫자의 평균이 아니라 역할 분리다.

| 측정 경로 | 제품 내 역할 | 해석 한계 |
|---|---|---|
| **검색 설정을 고정한 API** | 주간 전체 측정과 조치 직후 검증의 공식 시계열 | 설정한 API 표면의 표준 관측치이며 소비자 전체 노출의 대리값이라고 단정하지 않음 |
| **통제 웹 UI 표본** | 실제 제품 경험과 API 추세의 대표성 차이 탐지 | 계정·Memory·프로필·요금제·표시 모델·검색 모드·IP/네트워크 위치의 영향을 받아 API 점수와 합산 불가 |

OpenAI·Claude·Gemini API는 검색 도구를 제공해도 모델이 실제 검색 여부를 판단할 수 있다. Perplexity도 검색 설정·필터를 별도로 가진다. 따라서 `search_policy`(`available_auto / forced / ui_default`)와 검색 호출·검색 표시·인용으로 확인한 `search_used`를 분리해 저장하고, 증거가 없으면 `unknown`으로 둔다. 검색을 끈 API는 이번 MVP 측정 범위에서 제외한다. 측정 경로·검색 정책이 달라지면 같은 시계열로 비교할 수 없고, UI의 정확한 빌드가 노출되지 않으면 API와 동일 모델이라고 판정하지 않는다. 다만 API와 UI의 모델 버전 문자열이 다르거나 UI 버전이 미공개라는 사실은 대표성 격차 측정을 막는 조건이 아니라, 그 격차를 동일 모델 실험으로 해석하지 못하게 하는 한계다.

로그아웃이나 시크릿 모드도 완전한 비개인화를 보장하지 않는다. ChatGPT·Claude는 IP 위치를, Gemini는 일반·정밀 위치를, Perplexity는 프로필 위치가 없을 때 네트워크 위치를 사용할 수 있다. 따라서 제품 문구는 `비개인화 UI`가 아니라 **통제 UI 표본**으로 제한한다.

자동화는 공식 API에만 적용한다. OpenAI 약관은 Output의 자동·프로그램식 추출을, Anthropic 소비자 약관은 API 또는 명시적 허용이 없는 자동·비인간 접근을 금지한다. Google은 기계 판독 지침을 위반하는 자동 접근을 금지하며 Perplexity UI 자동화 허용 범위는 확인하지 못했다. 별도 허용 전 UI는 수동 또는 사용자 보조 표본으로 운영한다.
