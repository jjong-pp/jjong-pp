면접에서는 결론과 선택 이유를 먼저 말합니다. 면접관이 더 물으면 검토했던 대안과 아직 확인하지 못한 부분을 덧붙입니다. 모든 답변을 같은 형식에 맞출 필요는 없습니다.

## 1. GEO 기초 지식

### 1-1. 이 과제에서 말하는 GEO

GEO는 아직 제품과 조직마다 범위를 다르게 쓰는 용어입니다. 이 문서에서는 생성형 AI가 브랜드와 정보를 발견하고 이해하는 과정을 관찰하고 개선하는 활동으로 한정합니다. 기술 적용 자체보다 다음 세 질문에 답하는 업무에 가깝습니다.

- 고객에게 중요한 질문에서 브랜드가 후보로 나오는가?
- 실제 강점과 맞는 이유로 설명되는가?
- 정보를 고친 뒤 같은 조건에서 결과가 달라졌는가?

GEO는 AI 답변을 통제하거나 노출을 보장하는 기술이 아닙니다. 질문, 제공사, 모델, 검색 사용 여부, 시점에 따라 결과가 달라질 수 있으므로 **관측한 범위와 조건을 함께 설명하는 일**이 중요합니다.

### 1-2. SEO와 GEO의 차이

| 구분 | SEO | 이 과제의 GEO |
|---|---|---|
| 주된 관측 대상 | 검색 결과의 페이지·순위·클릭 | 생성된 답변 속 브랜드의 등장·추천·설명 |
| 사용자의 다음 행동 | 링크를 선택해 페이지로 이동 | 답변 안에서 후보를 만들거나 추가 탐색 |
| 측정 단위 | 검색어·노출·순위·클릭 | 목표 질문·반복 답변·등장 역할·원문 근거 |
| 변동 요인 | 검색 알고리즘·지역·기기·시점 | 질문 표현·모델·검색 사용·생성 변동·시점 |
| 품질 문제 | 순위가 낮거나 클릭되지 않음 | 많이 나와도 틀린 이유로 소개될 수 있음 |
| 주요 대응 | 페이지 구조·콘텐츠·링크 개선 | 질문 선정·사실 정보 정리·출처별 수정·재확인 |

SEO의 원리를 버리는 것이 아니라 관측 단위가 달라진다고 보는 편이 정확합니다. 검색 친화적인 구조와 신뢰할 수 있는 콘텐츠는 GEO에도 도움이 될 수 있지만, 검색 순위가 곧 AI 답변 속 추천을 뜻하지는 않습니다.

### 1-3. AI 답변이 만들어지는 흐름

제품마다 구현은 다르지만 면접에서는 다음 정도로 이해합니다.

```text
사용자 질문
→ 모델의 내부 지식과, 기능이 켜진 경우 검색·검색증강 결과
→ 생성된 답변과 함께 표시된 인용
→ 제품이 답변의 브랜드 역할과 추천 이유를 분석
→ 고객이 승인한 기준 정보와 별도로 대조
```

여기서 주의할 점은 세 가지입니다.

1. 검색 기능이 켜져 있어도 제공사마다 실행 방식과 공개 정보가 다릅니다.
2. 인용 URL이 함께 나왔다고 해서 특정 문장의 원인이 그 URL이라고 단정할 수 없습니다.
3. API와 소비자용 화면은 모델·시스템 지시·검색·개인화 조건이 다를 수 있으므로, 별도 확인 없이 한쪽 결과가 다른 쪽을 대표한다고 보지 않습니다.

서로 혼동하기 쉬운 상태도 구분합니다.

| 상태 | 알 수 있는 것 | 아직 알 수 없는 것 |
|---|---|---|
| 크롤러 방문 | 식별된 크롤러가 페이지를 요청한 기록이 있다 | 콘텐츠를 정상 수집·색인했거나 답변에 사용했는가 |
| 인용 | 답변에 출처 링크가 함께 제시됐다 | 특정 문장이 그 출처 때문에 생성됐는가 |
| 언급 | 브랜드 이름이 답변에 등장했다 | 실제 추천 후보로 평가됐는가 |
| 추천 | 브랜드가 적합한 후보나 선택지로 제시됐다 | 설명이 사실과 맞고 구매에 영향을 줬는가 |

### 1-4. 왜 한 번이 아니라 반복해서 보는가

생성형 답변은 같은 질문에서도 달라질 수 있습니다. 제출본에서 인용한 2026년 사전연구는 동일한 상업 추천 질문을 반복했을 때 추천 브랜드 집합의 평균 중첩도가 0.50~0.61이었다고 보고했습니다. 뜻을 유지한 표현 변형끼리의 중첩도도 낮았습니다.[1]

이 수치를 한국어 목표값으로 쓰지는 않습니다. 가져온 결론은 다음 두 가지뿐입니다.

- 한 번의 스크린샷을 성과로 판단하지 않는다.
- 같은 의도를 가진 표현과 반복 실행을 함께 보되, 결과를 전체 시장 확률로 일반화하지 않는다.

## 2. 측정 개념과 용어

### 2-1. 목표 질문과 대표 표현

**목표 질문**은 고객 문제, 구매 상황, AI 답변을 본 뒤 기대하는 행동에서 만든 질문입니다. 모든 질문을 많이 측정하는 것이 아니라 사업에 중요한 질문을 먼저 고릅니다.

**대표 표현**은 같은 의도를 자연스럽게 다르게 말한 문장입니다. 한 문장을 구매 의도 전체의 대리값으로 쓰지 않기 위해 사용합니다. 정확한 표현 수는 결과 편차와 비용을 본 뒤 조정합니다.

AI는 질문 초안을 만들 수 있지만 최종 질문을 정하지 않습니다. 공개 FAQ와 개인정보 없이 요약한 반복 문의를 참고하고 담당자가 문구와 중요도를 승인합니다.

### 2-2. 노출과 추천은 다르다

- **노출:** 답변에 브랜드 이름이 등장했다.
- **추천:** 답변이 브랜드를 적합한 후보로 제시했다.
- **비교 후보:** 다른 제품과 함께 검토 대상으로 다뤘다.
- **단순 언급:** 이름은 나왔지만 선택 이유가 없다.
- **주의·비추천:** 제약이나 부적합 이유와 함께 제외했다.

면접에서 사용할 기본 정의:

> 노출률은 유효 실행 중 브랜드가 등장한 비율이고, 추천률은 실제 추천 후보로 제시된 비율입니다. 둘은 같은 값이 아니며 역할 판정에는 원문 근거가 필요합니다.

이 비율의 분모는 전체 시장이 아닙니다. 사용자가 승인한 질문과 표현, 선언된 실행 환경, 유효한 반복 실행의 수입니다.

### 2-3. 사실 정확성과 사람 확인

브랜드가 많이 나와도 요금, 기능, 지원 범위가 틀리면 좋은 GEO로 보지 않습니다. 자동 분석은 오류 후보와 관련 문장을 찾는 데 사용하고, 실제 오류 여부는 고객이 승인한 공식 정보와 사람이 대조해 결정합니다.

애매한 내용은 억지로 맞음·틀림으로 나누지 않고 판단 불가로 남깁니다. 첫 파일럿에서 볼 값은 다음과 같습니다.

- 자동 판정과 사람 확인 결과의 일치율
- 판단 불가 비율
- 답변 한 건을 검토하는 데 걸린 시간
- 고객이 반복해서 고친 분류와 사실 항목

### 2-4. 전후 비교와 인과관계

정보를 수정한 뒤 같은 질문의 답변이 달라져도 “그 수정 때문에 좋아졌다”고 단정하지 않습니다. 같은 질문과 가능한 한 같은 조건에서 함께 관측된 변화라고만 표현합니다.

질문 세트, 모델, 검색 조건처럼 비교에 중요한 환경이 달라지면 같은 추이로 합치지 않습니다. 색인·크롤링 지연과 모델 변경도 결과에 영향을 줄 수 있습니다.

### 2-5. API와 소비자 화면

- API는 실행 조건을 기록하고 반복하기 상대적으로 좋습니다.
- 소비자 화면은 실제 사용 경험과 가깝지만 개인화·UI·검색 조건을 통제하기 어렵습니다.
- 두 경로는 서로 다른 관측 환경이며 결과를 합산하지 않습니다.

V1에서는 API 시계열과 소비자 화면 표본을 함께 운영하는 구조까지 검토했습니다. V2에서는 수집 체계를 두 개 만들기 전에 디자인 파트너가 실제로 궁금해하는 한 환경에서 고객 가치를 먼저 확인합니다.

답변 수집은 해당 서비스가 제공하는 공식 접근 방식과 이용 조건을 먼저 확인합니다. 소비자 UI 자동화를 당연한 전제로 두지 않으며, 반복 수집이 허용되지 않는 환경은 제품 지표에서 제외합니다.

## 3. 과제의 전체 의도와 지원자의 방향

### 3-1. 문제의 출발점

과제의 사용자는 “ChatGPT 등 AI 답변에 우리 브랜드가 얼마나, 어떻게 나오는가”를 알고 싶어 합니다. 단순히 이름이 나온 횟수를 세는 것만으로는 다음 질문에 답하기 어렵습니다.

- 어느 질문에서 나왔는가?
- 추천된 것인가, 이름만 언급된 것인가?
- 왜 추천되거나 제외됐는가?
- 설명이 실제 제품 정보와 맞는가?
- 담당자가 이번 주에 무엇을 해야 하는가?

### 3-2. 이 과제에 반영한 가치관

사용자가 대화에서 반복해서 선택한 방향은 다음과 같습니다.

1. 기술이 좋다고 설명하기보다 고객이 왜 도입하려는지 먼저 묻는다.
2. 전체 언급량보다 어떤 질문에서 많이 나오는지가 중요하다.
3. 고객 문제에서 질문 후보를 만들고, 사업 기여도와 브랜드 적합도로 우선순위를 정한다.
4. 사실 정확성은 기본 조건으로 두고, 그 위에서 사업에 중요한 노출과 추천을 본다.
5. 제품은 현재 상태만 보여주지 않고 다음 행동을 정하게 해야 한다.
6. 다만 콘텐츠 작성과 실행을 대신하기보다 근거를 보여주고 사람이 결정하게 한다.

이를 한 문장으로 줄이면 다음과 같습니다.

> 기술을 먼저 파는 대신 고객의 문제를 측정 가능한 질문으로 바꾸고, 그 결과를 설명 가능한 행동으로 연결한다.

### 3-3. 핵심 사용자

주 사용자는 한국어 시장에서 구독형 협업툴의 SEO·콘텐츠·브랜드 업무를 함께 맡는 마케팅·그로스 담당자입니다. 이 사용자는 다음 상황에 놓여 있습니다.

- 대표나 CMO가 AI 답변 속 브랜드 상태를 묻는다.
- 직접 검색한 화면은 있지만 결과가 들쭉날쭉하다.
- 경쟁 서비스가 선택된 이유가 정리돼 있지 않다.
- 보고는 할 수 있어도 무엇을 먼저 바꿀지 결정하기 어렵다.

현재 시나리오는 사용자 인터뷰 결과가 아니라 과제와 실무 경험에서 만든 가설입니다. 첫 파일럿에서 실제 담당자의 문제 순서가 맞는지 검증해야 합니다.

### 3-4. 실제 경험 카드 — 사용자 작성

현재 제출본의 유일한 큰 공백은 재직사 경험에서 본인이 직접 한 일이 구체적으로 보이지 않는다는 점입니다.

| 항목 | 작성할 내용 |
|---|---|
| 당시 직무 |  |
| GEO 검토 시기와 계기 |  |
| 본인이 직접 맡은 역할 |  |
| 직접 한 행동 |  |
| 만든 문서·분석·회의 산출물 |  |
| 그 뒤 바뀐 결정 |  |
| 확인한 결과 또는 배운 점 |  |
| 공개하면 안 되는 정보 |  |

제출본에 넣을 문장 구조:

> 당시 저는 **[실제 역할]**로 **[직접 한 행동이나 만든 산출물]**을 맡았고, 그 과정에서 **[바뀐 결정 또는 확인한 결과]**를 경험했습니다.

직접 도입을 실행한 것이 아니라 논의에 참여한 경험이라면 범위를 낮춰 말합니다.

> 제가 직접 도입 결정을 내린 것은 아니지만 현업 논의에 참여하며, 기술 설명만으로는 적용할 업무와 성공 기준이 정해지지 않는 과정을 봤습니다.

## 4. 좋은 GEO 기준 3개

| 기준 | 묻는 질문 | 필요한 이유 | 연결되는 기능 |
|---|---|---|---|
| 중요한 질문에서 반복해 후보가 되는가 | 어디에서 얼마나 나오는가 | 중요하지 않은 질문의 언급량이 성과를 가리는 것을 막음 | 기능 1 |
| 맞는 이유로 추천되는가 | 어떻게, 왜 나오는가 | 틀린 정보와 부적합한 추천을 좋은 노출로 세지 않음 | 기능 2 |
| 고친 뒤 유지되거나 나아지는가 | 행동 뒤 무엇이 달라졌는가 | 일회성 보고서를 다음 결정에 쓰이는 업무로 바꿈 | 기능 1 재확인 |

세 기준의 순서는 다음과 같습니다.

```text
고객 문제에서 중요한 질문을 고른다
→ 노출과 추천 상태를 본다
→ 답변의 역할·이유·사실을 확인한다
→ 행동 하나를 정한다
→ 같은 질문을 다시 본다
```

## 5. 기능 2개의 의도와 범위

### 기능 1. 목표 질문 노출·추천 현황

**사용자의 질문:** 중요한 질문에서 우리 브랜드가 얼마나 노출·추천되는가?

**입력:** 도입 이유, 대상 고객, 구매 상황, 기대 행동, 승인된 목표 질문

**출력:** 질문별 노출률·추천률, 경쟁사 대비 위치, 회차별 편차, 답변 원문

**사용자의 결정:** 가장 먼저 살펴볼 질문 하나

하나의 종합점수를 두지 않은 이유는 질문 가중치와 역할 판정이 검증되지 않은 상태에서 숫자 하나가 과도한 확신을 줄 수 있기 때문입니다.

### 기능 2. 답변 진단·우선 행동 카드

**사용자의 질문:** 답변에서 어떻게 등장했고 무엇을 먼저 할 것인가?

**입력:** 기능 1에서 고른 질문의 답변, 고객이 승인한 공식 정보

**출력:** 등장 역할, 추천·제외 이유, 원문 근거, 사실 차이, 행동 카드 한 장

**사용자의 결정:** 제안된 행동을 이번 주에 실행할지 여부

첫 구현은 질문 하나에서 모은 답변, 역할 네 종류, 요금·기능·지원 범위만 다룹니다. 프로젝트 관리, 자동 콘텐츠 생성, 외부 사이트 수정 대행은 포함하지 않습니다.

행동 카드는 고객에게 중요한 질문에서 같은 문제가 반복된 경우를 먼저 올립니다. 원문 근거가 분명할 때만 자사 정보 수정, 제3자 정보 갱신 요청, 제품 근거 보완 중 하나를 제안합니다. 애매하면 행동을 권하지 않고 공식 정보와 다시 대조합니다.

### 왜 이 두 기능이 먼저인가

상태를 보지 않고 행동을 권하면 제안 이유를 설명할 수 없습니다. 반대로 현황만 보여주면 담당자가 다시 혼자 해석해야 합니다. 기능 1은 문제 질문을 고르고, 기능 2는 그 질문에서 실행할 행동을 정하게 합니다.

## 6. 첫 검증과 다음 결정

### 6-1. Concierge MVP

처음부터 모든 수집·분류·카드 작성을 자동화하지 않습니다.

| 운영자가 뒤에서 하는 일 | 고객이 하는 일 |
|---|---|
| 질문 후보와 AI 답변 정리, 역할·사실 후보 검수, 행동 카드 초안 | 목표 질문·기준 정보 승인, 문제 답변 선택, 최종 행동 결정, 재확인 요청 |

가장 큰 가설은 자동 분류 기술이 아니라 고객이 이 진단으로 실제 행동을 정하느냐입니다. 계정별 처리 시간과 고객이 고친 부분을 기록한 뒤 여러 계정에서 반복되는 일부터 자동화합니다.

### 6-2. 성공 측정

| 단계 | 볼 값 | 확인하려는 것 |
|---|---|---|
| 첫 가치 | 온보딩부터 첫 현황표까지 걸린 시간과 완료율 | 고객 문제가 측정 질문으로 바뀌는가 |
| 의사결정 | 문제 답변을 열고 제안 행동을 실행하기로 정한 계정 비율 | 결과가 이번 주 우선순위 결정에 쓰이는가 |
| 재확인 | 행동 뒤 같은 질문을 다시 확인한 계정 비율 | 두 기능이 일회성 보고서로 끝나지 않는가 |
| 분석 신뢰 | 사람 확인 표본의 역할·사실 판정 일치율과 판단 불가율 | 행동 카드에 쓸 만큼 판정이 믿을 만한가 |
| 수동 운영 | 계정별 처리 시간과 고객이 반복해서 고친 단계 | 무엇부터 자동화할 수 있는가 |
| 관측 결과 | 비교 가능한 재확인에서 추천 역할이 개선되거나 사실 오류가 해소된 비율 | 수정 뒤 추천 역할이나 사실 정확성이 나아졌는가 |

### 6-3. 진행·수정·중단 기준

**다음 단계로 진행:** 디자인 파트너의 과반이 백오피스 수동 처리 외에 별도 안내를 받지 않고 질문을 승인하며, 행동 카드를 실제 업무에 쓰고 재확인을 요청한다.

**화면과 흐름 수정:** 참여사의 과반이 같은 단계에서 막히거나 행동을 고르지 못한다.

**해당 유형의 자동 제안 중단:** 사람 확인 뒤 역할·사실 판정이 바뀌어 추천 행동까지 달라진 경우, 그 오류 유형의 자동 제안을 멈춘다.

**자동화 보류:** 계정마다 수동 작업이 모두 달라 공통 단계를 찾지 못한다.

과반은 시장 성공률이 아니라 한두 곳의 좋은 반응만으로 추가 개발을 결정하지 않기 위한 내부 기준입니다. 디자인 파트너 수와 선정 기준은 실제 모집 전에 확정해야 하는 운영 가설입니다.

## 7. V1에서 V2로 줄인 배경

V1은 가능한 제품의 전체 범위와 기술 위험을 파악하는 데 도움이 됐습니다. 그러나 제출 질문은 “가장 필요한 기능 2개”를 요구했고, V1의 기능은 여러 시스템이 묶인 에픽에 가까웠습니다.

| V1에서 탐색한 것 | V2에서 남긴 것 | 줄인 이유 |
|---|---|---|
| 종합점수·상태 등급 | 질문별 원지표와 원문 | 가중치가 검증되지 않음 |
| API와 소비자 UI 동시 운영 | 고객이 고른 한 측정 환경 | 첫 가치 확인 전에 운영 범위가 큼 |
| 주간·월간 지속 감시 | 수정 뒤 한 번의 재확인 | 반복 사용 수요와 비용이 미확인 |
| 중대 오류 상태·재발 관리 | 사람 확인이 포함된 오류 후보 | 프로젝트 관리 제품으로 팽창 |
| 자동 기준 정보 추출 | 고객 승인 사실 항목 | 제품이 정답을 임의로 확정할 위험 |
| 과제의 일정·담당자 관리 | 행동 카드 한 장 | 사용자의 첫 결정에 필요하지 않음 |

V2에서 확인하려는 것은 두 가지입니다.

- 고객이 먼저 볼 질문을 고를 수 있는가?
- 그 답변에서 이번 주에 할 일을 정할 수 있는가?

V1의 상세 설계는 폐기한 약속이 아니라 후속 질문에 답하기 위한 탐색 기록입니다. 고객 가치와 운영 비용이 확인된 항목만 다시 가져옵니다.

## 8. 근거 자료와 해석 범위

| 자료 | 이 과제에 사용한 결론 | 사용하지 않은 결론 |
|---|---|---|
| Jack et al. 사전연구[1] | 같은 추천 질문도 결과가 달라 반복이 필요함 | 한국어 목표값·충분한 반복 횟수 |
| Bain[2] | 제3자 출처의 중요성과 일부 구매자의 재탐색 행동 | 국내 협업툴 시장 규모·전환율 |
| Forrester[3] | B2B 구매 과정에서 AI 사용이 넓어지고 있음 | AI 노출이 매출을 만든다는 인과 |
| Profound FactCheck[4] | 주장 추출과 기준 정보 대조의 구현 가능성 | 우리 분류가 이미 정확하다는 증거 |
| QSHOP 공개 기능[5] | 페이지 구조·메타 정보·크롤러 이력과의 연결 가설 | 내부 데이터·기술 구조·로드맵 |

### 8-1. 사실 상태와 설명 범위

| 상태 | 내용 |
|---|---|
| **확인됨** | V2가 최종 제안이며 V1은 탐색본이다. 사용자 인터뷰와 파일럿은 실행하지 않았다. QSHOP 내용은 공개 페이지에서만 확인했다. |
| **계획** | 한 측정 환경에서 Concierge MVP를 진행하고, 사람이 역할·사실 후보를 검수하며, 행동 뒤 한 번 재확인한다. |
| **아직 모름** | 디자인 파트너 수와 선정 기준, 첫 AI 서비스와 수집 경로, 한국어 기준선, 계정당 비용, 반복 사용 수요와 지불 의사, QSHOP 내부 로드맵 |

면접에서는 다음 경계를 넘지 않습니다.

- 실행하지 않은 인터뷰·파일럿·측정을 실제 결과처럼 말하지 않습니다.
- API 결과와 소비자 화면이 같다고 말하지 않습니다.
- 수정 행동이 답변 변화를 만들었다고 인과관계를 주장하지 않습니다.
- 해외 자료를 국내 협업툴 시장 규모나 목표값으로 사용하지 않습니다.
- V1의 점수 산식이나 반복 횟수를 검증된 업계 기준이라고 말하지 않습니다.
- Concierge 수동 작업을 구현된 자동 기능처럼 말하지 않습니다.

### 8-2. 생성형 AI 활용 범위

생성형 AI는 공개 자료 후보 탐색, 인용 원문 대조, 측정 방식의 예외 점검, 문장의 반복과 모호한 표현 검토에 사용했습니다. 문제 정의와 기능 우선순위는 지원자가 직접 정했으며, 실행하지 않은 파일럿 결과나 확인하지 않은 수치는 넣지 않았습니다.

## 9. 스퀘어스·큐샵과 연결한 이유

큐샵은 공개 페이지에서 AI가 읽기 쉬운 텍스트 구조, 메타 정보 처리, AI 크롤러 방문 이력 대시보드를 설명하고 있습니다.[5]

이번 제안은 다음 단계로 이어집니다.

```text
AI 크롤러가 페이지를 방문했는가
→ 중요한 질문의 답변에 브랜드가 나왔는가
→ 어떤 역할과 이유로 나왔는가
→ 고칠 정보가 있다면 관련 큐샵 페이지로 이동한다
```

별도 GEO 플랫폼보다 큐샵 안에 두자는 것은 공개 기능에서 세운 가설입니다. 고객이 이 연결을 중요하게 보지 않는다면 직접 구축보다 기존 제품과의 연동을 검토해야 합니다.

## 10. 예제 면접 질문

아래 질문은 답을 외우기보다 앞의 내용을 자신의 말로 설명하는 연습에 사용합니다.

### 1. 실제 GEO 검토에서 무엇을 겪었고 본인이 직접 한 일은 무엇입니까?

답변에 포함할 내용:

- 당시 직무와 본인의 권한
- 직접 한 행동과 만든 산출물
- 그 뒤 바뀐 결정 또는 확인한 결과
- 팀이 한 일과 본인이 한 일의 구분

### 2. 좋은 GEO 기준을 왜 이 세 가지로 정했습니까?

답변에 포함할 내용:

- 전체 언급량보다 중요한 질문이 먼저라는 판단
- 많이 나와도 틀리게 설명되면 성과가 아니라는 점
- 수정 뒤 다시 보지 않으면 일회성 보고서라는 점

### 3. 왜 기능 1과 기능 2가 가장 먼저입니까?

답변에 포함할 내용:

- 기능 1의 결정은 확인할 질문 하나
- 기능 2의 결정은 실행할 행동 하나
- 자동 콘텐츠와 프로젝트 관리를 제외한 이유

### 4. 목표 질문은 어떻게 만들고 노출률·추천률의 범위는 어디까지입니까?

답변에 포함할 내용:

- AI는 질문 초안만 제안
- 공개 FAQ·비식별 반복 문의·담당자 승인
- 분모는 승인 질문·선언 환경·유효 실행
- 시장 전체 확률이나 검색량이라고 주장하지 않음

### 5. 기능 2는 여러 기능을 한데 묶은 것 아닙니까?

답변에 포함할 내용:

- 안쪽 구현 요소는 여러 개라는 점을 인정
- 사용자 결정은 행동 하나
- 질문 하나·역할 네 종류·승인 사실 정보·카드 한 장으로 제한
- 수동 비용이 크면 사실 항목부터 더 축소

### 6. 왜 Concierge MVP이며 어떤 결과가 나오면 개발을 멈춥니까?

답변에 포함할 내용:

- 운영자와 고객의 역할 구분
- 디자인 파트너 과반이 백오피스 수동 처리 외 별도 안내 없이 질문 승인→행동 사용→재확인 요청을 마치는 조건
- 화면 문제, 판정 문제, 공통 자동화 부재를 구분
- 과반은 시장 통계가 아니라 내부 투자 판단선

### 7. V1의 종합점수와 여러 측정 환경을 왜 V2에서 뺐습니까?

답변에 포함할 내용:

- V1은 전체 가능성 탐색, V2는 최종 제안
- 검증되지 않은 정밀도와 운영 비용
- 원지표 이해와 반복 사용이 확인된 뒤 재검토

### 8. 왜 큐샵 안에 두는 것이 적합합니까?

답변에 포함할 내용:

- 크롤러 방문 다음 단계인 실제 답변 관측
- 문제 발견에서 페이지 수정까지의 거리 단축
- 공개 정보 기반 가설이며 고객 검증이 필요함
