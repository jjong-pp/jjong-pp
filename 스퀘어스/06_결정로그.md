1. 한 번에 핵심 질문 하나를 다룬다.

6. 검증된 선택을 문항 1·문항 2에 구체화한다.
7. 확정된 선택을 이 결정 로그와 전체 답안에 반영한다.

## 3. 진행 중인 결정

### 결정 01 — 고객의 가장 큰 문제

- 상태: **확정**

#### 사용자 1차 답변

- 1순위: **B. 행동 결정 불능**
- 2순위: **C. 조직 설득 불능**
- 현업에서 GEO 도입을 시도했을 때 기술 자체보다 `어디에 쓰고 어떤 페인포인트를 해결하는가`를 연결하지 못하는 문제가 컸다.
- 공급자가 “우리 기술이 좋다”고 설명하는 것보다 고객에게 왜 문의했는지, 어떤 문제가 있는지 먼저 묻고 그에 맞는 해결책을 찾아줘야 한다.
- 행동 방향과 결과가 생기면 조직을 설득할 자료도 자연스럽게 만들어진다.

#### 답변 정제

- **A. 판단 근거 제공은 기본 계측층**으로 전제한다.
- **B. 고객 맥락에 맞춘 우선순위 제안이 제품의 핵심 가치**다.
- **C. 실행 대행은 MVP 범위 밖**이다. 실제 콘텐츠 작성·외부 출처 수정·운영 대행은 더 깊은 계약이나 별도 서비스가 필요한 영역이다.
- 제품은 결과를 보여주는 데서 끝나지 않고, 결과를 바탕으로 다음 단계까지 계속 제안해야 한다.

#### 문제 구조

```text
고객 목표·문제 파악
→ AI 답변 노출 측정(A: 기본 계측)
→ 원인과 기회 해석
→ 다음 행동의 우선순위 제안(B: 핵심 가치)
→ 사용자 실행
→ 재측정
→ 다음 우선순위 제안
→ 조직 공유·설득(C: 결과)
```

#### 추가 조사와 선택 검증

- 큐샵은 현재 AI 봇 방문, `llms.txt`, 구조화 데이터를 제공하고 실제 AI 답변의 인용 추적을 다음 업데이트로 예고했다. 따라서 `기술적 준비 상태 → 실제 노출 결과 → 행동 제안`은 기존 자산의 자연스러운 다음 단계다.
- Profound Projects는 “대시보드는 이번 주 무엇을 해야 하는지 알려주지 않는다”는 문제를 명시하고 목표·데이터 기반 작업을 제안한다.
- Waikay Action Plans는 업종·경쟁사·발견된 격차를 반영해 행동을 영향도·실행 용이성으로 정렬한다.
- Scrunch도 Observe → Understand → Deliver 구조와 우선 추천을 제공한다.
- 따라서 **행동 제안 자체를 시장의 빈칸이나 독점적 차별점으로 주장하지 않는다.** 고객 요구를 충족하는 필수 가치로 보고, 큐샵의 제작·수정 환경과 연결 가능한 점을 회사 자산상의 강점으로 다룬다.

#### 답안에 적용할 핵심 문장

> 담당자의 문제는 AI 답변에서 자사 브랜드가 얼마나 노출되는지 모른다는 데서 끝나지 않는다. 노출 결과를 확인해도 그것이 자신의 사업 목표와 어떤 관련이 있고, 무엇부터 바꿔야 하는지 판단하기 어렵다. 따라서 제품은 고객의 목표와 현재 문제를 먼저 파악하고, 측정 결과를 실행 우선순위로 번역해야 한다.

#### 전체 답안 영향

- F1은 고객이 판단할 수 있는 기준선을 만드는 **필수 계측 기능**으로 정의한다.
- F2는 고객 맥락과 측정 근거를 바탕으로 다음 행동을 정렬하는 **핵심 가치 기능**으로 검토한다.
- 공유 리포트는 별도 핵심 기능이 아니라 F1·F2의 결과물로 둔다.
- 자동 실행·콘텐츠 생성·외부 수정 대행은 1차 릴리즈에서 제외한다.
- 성공 측정에는 `제안 행동 채택`, `실행 후 재측정`, `다음 제안 확인`으로 이어지는 순환을 포함한다.

### 결정 02 — 제품이 먼저 파악해야 할 고객 맥락

- 상태: **확정**

#### 사용자 1차 답변

- 고객에게 가장 먼저 물어야 할 것은 **왜 GEO를 도입하려고 하는지**, 그리고 **이를 통해 무엇이 달라지기를 기대하는지**다.
- 처음부터 후보군 진입·오정보 수정 같은 기술적·제품 중심 분류를 묻기보다 고객이 가진 문제와 기대를 먼저 이해해야 한다.

#### 답변 정제

- 완전한 자유 서술형만 사용하지 않는다.
- GEO 도입 과정을 단계별로 나눈 **선택형 카드**로 고객이 생각을 정리할 수 있게 한다.
- 마지막에 카드로 담기지 않은 배경과 기대를 자유롭게 입력하게 한다.
- AI가 선택값과 서술형 답변을 종합해 `도입 목적·대상 고객·기대 변화·측정 방향`으로 구조화한다.
- AI의 해석을 그대로 확정하지 않고 고객이 수정·승인하게 한다.

#### 확정된 온보딩 구조

| 단계 | 고객에게 묻는 것 | 방식 |
|---|---|---|
| 1. 도입 계기 | 왜 지금 AI 답변 노출을 확인하려고 하는가 | 상황 선택 카드 + 기타 |
| 2. 기대 변화 | 사용 후 무엇이 달라지기를 기대하는가 | 결과 선택 카드 + 복수 선택 |
| 3. 고객·구매 상황 | 누구의 어떤 질문과 결정에서 달라져야 하는가 | 페르소나·여정 카드 |
| 4. 추가 맥락 | 앞선 선택에 담기지 않은 배경·제약은 무엇인가 | 짧은 자유 서술 |
| 5. 목표 확인 | AI가 이해한 목표와 측정 방향이 맞는가 | AI 요약 + 직접 수정·승인 |

#### 추가 조사와 선택 검증

- Scrunch와 Profound는 브랜드, 경쟁사, 페르소나, 지역, 주제, 추가 맥락을 구조화해 질의 생성에 사용한다. 선택형 구조가 측정 설계에 필요한 데이터를 확보한다는 시장 근거다.
- Scrunch는 입력된 브랜드 맥락을 바탕으로 추천 주제와 프롬프트를 생성하되 사용자가 검수하도록 한다.
- Material Design의 choice/input chip은 정해진 선택과 입력값 검증·수정을 함께 지원한다.
- Nielsen Norman Group 자료는 고정 분류만 강제하면 사용자의 설명과 예외가 사라질 수 있으므로 자유 입력 경로를 함께 제공할 필요가 있음을 보여준다.
- 공개된 경쟁 제품 문서만으로는 `왜 지금 도입하는가`를 첫 질문으로 삼는지 확인되지 않았다. 따라서 이를 시장의 확정된 빈칸이라고 주장하지 않고, 사용자 경험에서 나온 **문제 발견 방식의 차이**로 제시한다.

#### 답안에 적용할 핵심 문장

> 정확한 질의 세트는 브랜드명과 경쟁사 목록만으로 만들어지지 않는다. 제품은 먼저 고객이 왜 지금 GEO를 확인하려는지와 무엇이 달라지기를 기대하는지를 단계별 선택으로 묻고, 마지막 자유 입력까지 AI가 종합한 목표를 고객이 직접 수정·확정하게 해야 한다.

#### 전체 답안 영향

- 온보딩은 기술 설정이 아니라 고객의 도입 계기와 기대 결과에서 시작한다.
- AI는 해결책을 바로 생성하기 전에 고객의 말을 측정 가능한 목표로 구조화한다.
- 질의 세트, 경쟁사, 우선 행동, 성공 지표는 확정된 목표에서 파생한다.
- 선택형 카드는 입력 부담과 데이터 편차를 줄이고, 마지막 서술형은 사전 분류가 놓친 맥락을 보완한다.

### 결정 03 — PRD의 1차 사용자

- 상태: **확정**

#### 사용자 1차 답변

- 가장 중요한 사용자는 마케팅·그로스 실무자와 브랜드를 만들어가는 담당자다.
- 특히 한국어로 고객을 획득하려는 이커머스·상업 브랜드 담당자에게 GEO가 중요하다.
- 이들은 SEO와 마찬가지로 AI 답변에서 브랜드가 더 많이, 더 긍정적으로 노출되는 방법을 고민한다.

#### 설명 후 답변 정제

- 선택: **B와 C**
  - B. 핵심 구매 질문에서 자사 브랜드가 정확한 추천 후보로 등장한다.
  - C. 브랜드가 긍정적인 맥락과 의도한 포지셔닝으로 설명된다.
- 여기서 제외한 것은 노출량 자체가 아니라 **중요도가 다른 질문을 구분하지 않고 합산한 총언급량**이다. 고객에게 중요한 목표 질문군 안에서의 반복 노출은 핵심 성과다.
- 따라서 **목표 질문군 내 노출·추천을 성과, C를 품질 조건**으로 둔다. 단, ‘긍정적’이라는 말은 무조건 호의적인 표현이 아니라 **검증된 사실과 일치하면서 브랜드의 실제 강점과 의도한 포지셔닝이 왜곡되지 않는 상태**로 제한한다.

#### 추가 조사와 선택 검증

- Bain은 B2B 구매자가 LLM에서 후보군을 만들 수 있으므로 단순 등장보다 구매 상황에서의 추천과 정확한 브랜드 묘사가 중요하다고 설명한다.
- Scrunch가 공개한 옵트인 클릭스트림 기반 관찰 연구에서는 이전에 관여하지 않았던 사용자에게 브랜드가 ‘추천’된 경우, 단순히 언급된 경우보다 이후 동명의 검색과 브랜드 사이트 방문이 더 크게 관찰됐다. 인과를 확정할 수 없는 벤더 연계 관찰 연구라는 한계가 있지만, **추천과 단순 언급을 분리해야 한다는 방향**은 뒷받침한다.
- Profound 등 현행 AI 가시성 제품도 언급량뿐 아니라 감성·포지셔닝을 별도 신호로 다룬다. 따라서 C는 독립적인 ‘좋은 말의 양’이 아니라 B의 추천 품질을 검증하는 조건으로 두는 편이 적절하다.

#### 구체화된 사용자 정의

> 1차 사용자는 한국어 기반 B2B SaaS의 소규모 마케팅·그로스 실무자다. SEO·콘텐츠·브랜드 업무를 함께 맡으며, 자사와 경쟁사가 핵심 구매 질문에서 어떤 이유로 추천되는지 확인하고 브랜드가 사실에 맞고 의도한 포지셔닝으로 설명되는지 판단한 뒤 이번 주의 개선 우선순위를 정해야 한다.

- **1차 사용자:** 한국어 기반 B2B SaaS 마케팅·그로스 실무자
- **2차 사용자:** 투자와 우선순위를 승인하는 대표·CMO
- **인접 확장 시장:** 한국어 이커머스·상업 브랜드 마케터. 스퀘어스의 기존 고객 자산과 연결되는 다음 시장으로만 제시하고, 이번 PRD의 1차 사용자로 섞지 않는다.
- **핵심 사용자 성과:** 고객에게 중요한 목표 질문군에서 반복적으로 노출·추천되고, 추천 이유와 브랜드 묘사가 실제 강점·의도한 포지셔닝과 일치하며, 다음 행동을 정할 수 있다.
- **지표 구분:** 목표 질문군 밖의 무작위 총언급량과 원시 합계는 보조 지표다. 목표 질문군 안에서 질문별 중요도를 반영한 가중 노출률·추천 점유율은 핵심 성과다.

#### 전체 답안 반영 방향

- PRD의 사용자와 시나리오는 ‘어디서나 많이’가 아니라 **고객에게 중요한 질문에서 많이, 올바르게 추천되게 만드는 실무자**를 중심으로 쓴다.
- F1은 목표 질문을 만드는 근거와 질문별 중요도, 원시 노출량, 가중 노출률·추천 점유율을 보여준다.
- F2는 단순 노출 증대가 아니라 추천 가능성과 묘사 품질을 막는 원인을 찾아 우선순위화한다.

### 결정 04 — GEO를 평가할 대표 질문의 범위

- 상태: **확정**

#### 사용자 교정

- 좋은 GEO라면 많이 노출되는 것은 당연히 중요하다.
- 핵심은 모든 질문의 노출량을 더하는 것이 아니라 **어떤 질문에서 우리를 많이 노출시킬 것인가**를 먼저 정하는 것이다.
- 최초 선택지는 인지도·구매 여정 단계 배분을 먼저 물어 질문의 순서가 맞지 않았다.

#### 답변 정제

> **고객 문제를 먼저 고려하고, 그 문제를 구체화하는 과정에서 사업 기여도와 브랜드 적합성을 고객에게서 유도한다.**

- **고객 문제는 질문 생성의 관문:** 어떤 고객이 어떤 상황에서 무엇을 해결하려는지 설명되지 않는 질문은 목표 질문에서 제외한다.
- **사업 기여도는 우선순위 축:** 해당 질문에서 노출·추천되면 브랜드 탐색, 비교, 체험, 도입 검토 등 어떤 다음 행동에 가까워지는지 고객의 목표와 KPI에서 도출한다.
- **브랜드 적합성은 정당성 축:** 실제로 잘 맞는 고객 조건, 검증 가능한 기능·사례·강점, 맞지 않는 조건을 받아 해당 질문에서 추천받을 자격이 있는지 확인한다.
- 사업 기여도와 브랜드 적합성은 회사가 임의로 정하거나 AI가 확정하지 않는다. 선택 카드와 자유 입력을 통해 고객에게서 끌어내고, AI가 구조화한 결과를 고객이 수정·승인한다.

#### 추가 조사와 선택 검증

- Jobs to Be Done 이론은 고객이 제품 속성 자체보다 특정 상황에서 이루려는 진전을 위해 제품을 선택한다고 본다. GEO 전용 연구는 아니지만 ‘제품명보다 고객 상황과 문제부터 묻는다’는 제품 철학의 근거가 된다.
- Google의 생성형 검색 공식 문서는 하나의 질문을 여러 하위 질문으로 확장하는 `query fan-out`을 설명한다. 이는 키워드 한 개보다 고객 문제에서 파생되는 질문군이 필요함을 보여주지만, Google AI 검색에 대한 설명이므로 ChatGPT 전체에 그대로 일반화하지 않는다.
- Scrunch는 모든 프롬프트를 추적하기보다 사업 관련 주제의 대표 표본을 만들고, 영업·고객 성공·지원 조직이 실제로 받는 질문을 입력으로 사용할 것을 권한다.
- Profound는 수많은 저가치 변형보다 전략 목표에 맞는 소수의 고영향 프롬프트를 우선하라고 권한다. 또한 실제 프롬프트 수요 데이터의 지역 범위가 제한적이므로 한국어 시장에서는 수요량만으로 질문을 고르기 어렵다.
- 따라서 이 결정은 검증된 단일 공식이라기보다 **고객 문제 발견 방식, 생성형 검색의 질문 확장 특성, 현행 시장의 프롬프트 운영 관행을 종합한 제품 설계 원칙**으로 제시한다.

```text
고객 문제·상황·대상 사용자 입력
→ 문제에서 후보 질문 생성
→ 질문별 기대 사업 행동과 기여도 확인
→ 검증 가능한 강점·사례·적합/비적합 조건으로 브랜드 적합성 확인
→ AI가 질문별 점수와 근거 제안
→ 사용자가 질문·점수·근거·포함 여부 수정 및 확정
→ 목표 질문군 내 가중 노출률·추천 점유율 측정
```

개념적으로 질문 우선순위는 다음과 같이 본다.

`질문 우선순위 = 고객 문제 적합성(필수 관문) × 사업 기여도 × 증거 기반 브랜드 적합성`

- 셋 중 하나가 0인 질문은 높은 검색량이 있더라도 핵심 목표 질문에서 제외하거나 장기 기회로 분리한다.
- SEO·PPC 키워드와 AI 주제 트렌드는 후보를 확장하고 통과한 질문끼리 수요를 보정하는 참고값으로 사용한다.
- 사업 기여도 점수는 질문의 우선순위를 정하는 선행 판단이며, GEO 노출이 실제 매출을 만들었다는 인과 증명으로 사용하지 않는다. 유입·체험·파이프라인은 별도의 후행 지표로 검증한다.
- 구매 여정 단계는 질문 생성의 출발점이 아니라, 확정된 질문 포트폴리오가 특정 단계에 과도하게 치우쳤는지 확인하는 분류값으로 사용한다.

#### 전체 답안 반영 방향

- 문항 1의 첫 기준을 **‘중요한 질문에서 재현되는 노출’**로 보정한다.
- F1에 고객 문제 기반 질문 생성, 사업 기여도·브랜드 적합성의 근거 제시, 사용자 확정, 가중 노출률·추천 점유율을 포함한다.
- 질문 세트나 가중치가 바뀌면 시계열이 GEO 개선처럼 보이지 않도록 버전을 분리한다.
- 성공 지표는 질문을 ‘직접 수정했는가’보다 고객이 목표 질문과 우선순위 근거를 이해하고 확정했는가를 본다.

### 결정 05 — 첫 번째 GEO 기준에서 ‘많이 노출’을 어떻게 계산할 것인가

- 상태: **확정**

#### 사용자 답변

- **C. GEO 종합 점수를 기본 전제로 제공한다.**
- 다만 실제로 중요하게 보고 판단할 것은 **B. 가중 노출률과 가중 추천률을 분리한 지표**다.
- 종합 점수는 DB와 산식이 지나치게 복잡해질 수 있으므로, 그보다 답변에 브랜드가 **어떻게 등장했는지**를 찾아내는 것이 더 중요하다.

#### 설명 후 답변 정제

C와 B는 양자택일이 아니라 서로 다른 층으로 둔다.

1. **요약층 — GEO 종합 상태:** 자사 절대 성과와 경쟁 위치를 원점수로 압축하되 사람이 P0로 확인했고 최신 상태가 `활성·해제 후보·재개방`인 미해결 이슈가 있으면 원점수는 보존하고 최종 등급만 제한
2. **판단층 — 두 개의 독립 축:** 자사 가중 노출률·추천률과 추이 / 경쟁사 대비 가중 추천 점유율. 선두 격차·평균 추천순위는 진단
3. **진단층 — 품질과 원문:** 추천 역할, 위치, 추천·제외 이유, 사실 오류, 포지셔닝, 인용 출처와 근거 원문

종합 점수는 데이터의 원천이 아니라 원자 지표를 요약한 **표현 레이어**다. 따라서 점수만 저장하거나 산식을 DB 컬럼에 고정하지 않고, 원문 답변과 원자 분석값을 보존한 뒤 버전이 붙은 산식으로 계산한다. 산식이 바뀌어도 과거 원문을 재분석하고 이전 점수와 구분할 수 있어야 한다.

#### ‘어떻게 등장했는가’의 측정 범위

| 구분 | 분류 예시 | 검증 방식 |
|---|---|---|
| 등장 역할 | 추천 / 비교·검토 후보 / 단순 언급 / 주의·비추천 | 판정 근거가 된 원문 문장 함께 제시 |
| 등장 위치 | 추천 순서, 첫 언급 위치, 답변 상·중·하 | 문자열 위치와 답변 구조로 계산 |
| 추천·제외 이유 | 가격, 보안, 사용성, 연동, 팀 규모 등 | 이유와 원문 근거 구절을 함께 추출 |
| 표현 방향 | 긍정 / 혼합 / 중립 / 부정 | 추천 여부와 별도 표시 |
| 사실 정확성 | 정확 / 부정확 / 판단 불가 | 고객이 승인한 요금제·기능·지원 범위와 대조 |
| 출처 | 자사 / 경쟁사 / 제3자 URL·도메인 | 인용 링크를 수집하되 답변을 만든 인과로 단정하지 않음 |

- 긍정적인 어조가 곧 추천을 의미하지 않는다. 반대로 담담한 문장도 강한 추천일 수 있으므로 `추천 역할`과 `감성`을 분리한다.
- 답변 상단에 있다는 사실은 가시성 신호지만 추천 강도의 대리값일 뿐, 추천 여부와 동일하게 취급하지 않는다.
- 인용 URL은 답변과 함께 제시된 근거이지 특정 문장을 인과적으로 만들었다는 증거가 아닐 수 있다.
- 자동 분류가 애매하면 억지로 확정하지 않고 `판단 불가`와 신뢰도를 제공하며 사용자가 원문을 보고 수정할 수 있게 한다.

#### 추가 조사와 기술 검증

- Scrunch의 공개 응답 구조와 가이드는 답변 원문, 브랜드 존재 여부, 위치, 감성, 경쟁사 동시 등장, 인용 URL과 프롬프트 맥락을 답변 단위로 저장·분석한다.
- Profound Sentiment는 브랜드 관련 표현을 테마·속성으로 나누고 판정의 정확한 원문 구절을 보여준다.
- Profound FactCheck는 브랜드 관련 사실 주장을 고객의 기준 정보와 대조해 정확·부정확 등을 분류한다.
- 따라서 `답변에 어떻게 등장했는가`의 분석은 기술적으로 실현 가능하다. 다만 검토한 공개 문서에서는 일반 B2B 답변의 `단순 언급 ↔ 실제 추천` 역할이 공통 표준 필드로 굳어 있지는 않았다. 이를 시장 전체의 확정된 공백이라고 주장하지 않고, MVP에서 검증해야 할 핵심 분류로 둔다.
- 구현 난이도의 중심은 DB보다 `질문 수 × 모델 수 × 반복 횟수 × 기간`에 따른 답변 수집 비용과 생성 변동성이다.

#### 최소 구현 구조

```text
원문 답변과 실행 조건 저장
→ 브랜드명·별칭 탐지
→ 위치는 규칙으로 계산
→ 추천 역할·이유·근거 구절은 의미 분류
→ 근거 구절이 실제 원문에 있는지 검증
→ 판단 불가·낮은 신뢰도는 사용자 검토
→ 원자 지표 집계
→ 버전이 붙은 산식으로 GEO 종합 점수 계산
```

- `answer_run`: 질문, 플랫폼, 모델, 언어, 시각, 원문
- `brand_appearance`: 브랜드, 역할, 순서·위치, 감성, 신뢰도, 근거 구절
- `claim/citation`: 속성·주장, 사실 대조 결과, URL·출처 유형
- `score_formula_version`: 종합 점수의 지표 구성과 가중치 버전

초기에는 답변 한 건의 원문과 분석 결과 JSON, 집계 테이블만으로도 구현할 수 있다. 원문을 불변 보존하고 역할 체계와 점수 산식을 버전형 설정으로 관리하면 DB에 점수를 하드코딩할 필요가 없다.

#### 전체 답안 반영 방향

- F1 상단에는 GEO 종합 점수를 두되, 바로 아래에서 가중 노출률·가중 추천률과 점수 구성 근거를 공개한다.
- 사용자는 종합 점수에서 목표 질문군 → 개별 질문 → 원문 답변과 등장 역할까지 내려갈 수 있다.
- 역할 분류에는 반드시 근거 원문과 신뢰도·사용자 수정 경로를 붙인다.
- F1은 등장 역할과 위치를, F2는 사실 정확성과 인용 출처를 중심으로 담당하되 같은 원문 데이터를 공유한다.
- 종합 점수의 비교 구조와 품질 가드레일은 결정 09, 자사 절대 성과 70 : 경쟁 위치 30은 결정 10, 절대 성과 내부 비중은 결정 11, 경쟁 위치 단일 지표는 결정 12에서 확정했다. 등급 경계는 후속 결정·파일럿에서 보정한다.

### 결정 06 — ‘추천’과 ‘단순 언급’을 어느 수준으로 구분할 것인가

- 상태: **확정**

#### 사용자 답변

- 추천안인 **B. 4단계 역할 분류**로 진행한다.

#### 설명과 답변 정제

MVP의 `등장 역할`은 다음 네 가지로 고정한다.

| 역할 | 판정 기준 | 가중 노출률 | 가중 추천률 |
|---|---|:---:|:---:|
| **추천** | 제품을 적합한 선택지로 명시적으로 제시 | 포함 | 포함 |
| **비교·검토 후보** | 후보군이나 비교표에는 포함되지만 선택을 지지하지 않음 | 포함 | 제외 |
| **단순 언급** | 사례·배경·기존 사용 제품 등으로 이름만 등장 | 포함 | 제외 |
| **주의·비추천** | 단점 경고, 부적합 조건, 후보 제외를 명시 | 포함하되 별도 경고 | 제외 |

`미노출`은 답변에 브랜드가 없다는 측정 결과이지 등장 역할이 아니므로 별도 상태로 둔다.

6단계에서 분리하려던 정보는 없애지 않고 **역할과 직교하는 보조 필드**로 저장한다.

- 주추천 여부와 추천 순서 → `recommendation_rank`
- 조건부 추천의 고객·상황 → `fit_condition`
- 대안으로 소개된 관계 → `alternative_to`
- 추천·제외 이유 → `reason/attribute`
- 긍정·혼합·중립·부정 → `sentiment`
- 판정 근거 → `evidence_text`
- 자동 판정의 불확실성 → `confidence`, `review_status`

이렇게 하면 “특정 조건에서 첫 번째로 추천된 대안”처럼 여러 속성이 동시에 성립하는 답변을 하나의 복잡한 역할 코드에 억지로 넣지 않아도 된다. 역할은 네 가지로 단순하게 유지하면서, 고객이 알고 싶은 세부 맥락은 필드 조합으로 보존한다.

#### 추가 조사와 선택 검증

- 상용 제품 문서에서 비교적 일관되게 확인되는 값은 브랜드 존재, 위치, 감성, 경쟁사, 인용과 원문이다.
- 일반 B2B 답변의 추천 역할은 공개된 공통 표준이 아니므로 처음부터 6단계 자동 분류를 전제로 하면 오분류와 검수 비용이 커질 수 있다.
- Scrunch의 관찰 연구는 추천과 단순 언급을 분리했을 때 후속 검색·방문 행동의 크기가 다르게 관찰됐다고 보고했다. 인과 실험은 아니지만 두 역할을 최소한 분리해야 한다는 근거로 사용할 수 있다.
- 따라서 4단계는 단순 이진 분류보다 고객 판단에 유용하면서도, MVP에서 한국어 원문을 표본 검수할 수 있는 범위다.

검증 출처:
- [From Prompt to Purchase 연구 원문](https://arxiv.org/abs/2606.10907)
- [Scrunch — 브랜드 노출 추적](https://scrunch.com/how-tos/how-to-track-brand-presence-in-ai-search/)
- [Profound — About Sentiment](https://help.tryprofound.com/articles/3189907319-about-sentiment)

#### 구현·검증 원칙

```text
존재 여부·문자 위치: 규칙 기반 계산
등장 역할·조건·이유: 의미 분류
근거 문장이 원문에 실제 존재하는지: 규칙 검증
애매한 결과: 판단 불가 및 사용자 검토
```

- 초기 한국어 답변 표본을 사람이 네 역할로 라벨링해 자동 분류 결과와 대조한다.
- 자동 판정에는 반드시 근거 원문을 붙이고, 사용자의 수정 결과를 이후 평가 데이터로 사용한다.
- 역할 분류 정확도가 확보되기 전에는 GEO 종합 점수에서 세부 역할별 임의 가중치를 크게 두지 않는다.

#### 전체 답안 반영 방향

- 가중 노출률은 네 역할 중 하나라도 등장하면 포함한다. 단, 주의·비추천의 비중은 옆에 경고 지표로 분리한다.
- 가중 추천률은 `추천` 역할만 포함한다.
- 주추천·조건부·대안 여부는 역할 개수를 늘리지 않고 순서·조건·관계 필드와 원문으로 보여준다.
- F1의 대표 화면은 `GEO 종합 점수 → 가중 노출률·추천률 → 네 역할 분포 → 원문` 순서로 내려간다.

### 결정 07 — 좋은 GEO의 세 번째 기준을 무엇으로 둘 것인가

- 상태: **확정**

#### 사용자 답변

- 추천안인 **B. 지속적인 개선 가능성**이 맞다고 판단했다.

#### 설명 후 답변 정제

‘지속적인 개선 가능성’만 쓰면 제품 기능이나 조직 역량처럼 들릴 수 있으므로, 좋은 GEO의 성과 기준은 다음처럼 정제한다.

> **성과의 지속성과 개선 효과의 검증 가능성:** 동일한 목표 질문·플랫폼·측정 조건에서 반복했을 때 전략적 노출과 바람직한 묘사가 유지되며, 실행 전후의 변화를 확인해 다음 결정을 갱신할 수 있는가.

- 좋은 GEO의 **상태**는 중요한 질문에서 원하는 방식의 노출·추천·정확성이 우연한 한 번이 아니라 유지되거나 개선되는 것이다.
- `원인 가설 → 행동 → 즉시 동조건 검증 → 주간 유지·재발 감시 → 다음 결정`은 그 상태를 증명하고 유지하는 **제품 메커니즘**이다.
- **A. 출처의 신뢰성과 최신성**은 독립적인 최종 성과가 아니라 원인 가설과 행동을 정하기 위한 진단 정보로 사용한다.
- **C. 실제 사업 기여**는 중요하지만 제로클릭·복수 접점·긴 B2B 구매 여정 때문에 직접 귀속하기 어려우므로 후행 검증 지표로 둔다.

#### 기존 기준의 논리 보정

기존의 `통제 가능 출처 비중이 높을수록 좋은 GEO`라는 정의는 폐기한다.

1. 신뢰할 수 있고 최신이며 사실에 맞는 제3자 출처는 자사가 통제할 수 없어도 좋은 추천 근거다.
2. 무브랜드 질문은 제3자 출처 의존도가 높아 자사 출처 비중 최대화가 구조적으로 부적절할 수 있다.
3. 인용 링크는 답변과 함께 관찰된 근거이지 해당 문장을 만든 인과라고 단정할 수 없다.
4. 따라서 출처의 신뢰성·최신성·사실 일치 여부는 **품질 진단**, 통제 가능성은 직접 수정·갱신 요청·보완 근거 확산을 구분하는 **행동 라우팅 정보**로 사용한다.

#### 추가 조사와 선택 검증

- Profound Projects는 가시성·인용·프롬프트 격차를 매주 분석해 근거와 작업 목록으로 전환하고, 대시보드만으로는 이번 주 무엇을 해야 하는지 알기 어렵다고 명시한다.
- Waikay Action Plans도 격차 발견 → 영향·난이도 기반 행동 우선순위 → 진행 → 점수 변화 추적의 흐름을 제공한다.
- Scrunch는 신뢰할 수 있는 반복 모니터링과 실험을 통해 상관관계와 인과를 구분해야 한다고 안내한다.
- Google은 신뢰할 수 있고 최신인 콘텐츠를 권장하지만 요구사항을 충족해도 생성형 검색 노출을 보장하지 않는다고 밝힌다. 따라서 출처 품질은 중요한 레버지만 단독 성과 기준은 아니다.
- 이 폐쇄 루프는 이미 경쟁 제품에도 있으므로 독점적 시장 공백이라고 주장하지 않는다. 고객 문제에서 출발한 소수의 행동을 한국어 실무자에게 제안하고 같은 측정 기준으로 닫는 구조가 이 PRD에서의 구체적 설계 판단이다.

- 이미 성과가 높은 브랜드도 있으므로 계속 상승만 요구하지 않고 **유지되거나 개선되는가**를 본다.
- 전후 차이는 모델 업데이트나 경쟁사 활동 때문일 수 있으므로 `우리 행동이 만들었다`고 단정하지 않고 `행동 이후 유의미한 변화가 관찰됐다`고 표현한다.
- 질문·가중치·언어·지역·모델·반복 규칙·산식 버전을 고정하고 비교 불가 구간을 분리한다.

#### 세 기준의 역할

- 기준 1: 중요한 질문에서 재현되는 노출 — **성과 기준선**
- 기준 2: 서술의 정확성과 역할 — **품질 가드레일**
- 기준 3: 성과의 지속성과 개선 효과의 검증 가능성 — **운영·학습 루프**
- 출처 신뢰성·최신성·통제 수준 — 기준 3의 **진단 및 행동 라우팅 정보**
- AI 유입·리드·파이프라인 — 세 기준 이후 확인하는 **후행 사업 지표**

#### 전체 답안 반영 방향

- F2를 `인용 출처 추적·서술 진단`에서 `서술·출처 진단과 개선 루프`로 확장한다.
- F2는 원인을 확정하지 않고 근거·신뢰도가 표시된 원인 가설을 제안한다.
- 핵심 성공 지표를 오류의 영구 소멸이 아니라 `행동 선택 → 실행 → 즉시 동조건 검증 → 주간 유지·재발 감시 → 다음 결정`의 루프 완료율과 현재 범위의 미재현·운영상 해제·재개방률로 바꾼다.
- 가중 노출률·추천률 또는 서술 품질의 변화는 고객 성과로, AI 유입·리드·파이프라인은 후행 사업 검증으로 분리한다.

### 결정 08 — F2가 개선 행동의 우선순위를 정하는 제1원칙

- 상태: **확정**
- 선택: **고객·사업 영향을 제1원칙으로 두고, 근거 신뢰도와 실행 효율은 보조 기준으로 사용**

#### 사용자 선택

- 사용자는 추천안대로 진행하기로 했다.
- 제품은 고객의 문제를 해결하는 데 집중해야 하므로, 실행하기 쉬운 과제보다 고객이 중요하게 여기는 질문의 격차를 먼저 다룬다.

#### 조사 후 보정

근거 신뢰도를 단순 동점 조정 기준으로만 두면 `고영향으로 추정되지만 근거가 거의 없는 행동`을 바로 실행하게 만들 수 있다. 따라서 최소 근거 수준을 관문으로 추가한다.

1. 고객 문제·목표 질문·기대 사업 행동과 관련이 없는 제안은 제외한다.
2. 최소 근거 수준에 미달하면 개선 행동이 아니라 검증 과제로 전환한다.
3. 목표 질문군에서 확인된 중대한 사실 오류는 기준 2의 품질 가드레일로 P0 처리한다.
4. 나머지는 고객·사업 영향 등급을 먼저 정한다. 영향은 `목표 질문 가중치 × 격차 심각도`로 설명하되 정밀한 인과 점수처럼 표현하지 않는다.
5. 같은 영향 등급에서는 근거 신뢰도가 높은 것을 먼저, 그다음 실행 노력·소요시간·가역성이 좋은 것을 우선한다.
6. 사용자는 제안 순서와 근거를 확인하고 조직 상황에 맞게 수정하며 변경 이유를 남길 수 있다.

`목표·최소 근거 관문 → 중대한 사실 오류(P0) → 고객·사업 영향 등급 → 근거 신뢰도 → 실행 효율`

여기서 P0는 모든 오탈자나 경미한 오류가 아니라, **타깃 고객의 선택을 잘못 이끌거나 고객사의 핵심 KPI에 영향을 주는 사실 오류**를 뜻한다. 즉 품질 가드레일도 고객·사업 영향 원칙의 예외가 아니라 높은 영향의 한 유형이다.

#### 선택 검증

- Waikay는 GEO 행동을 잠재 영향과 실행 용이성으로 정렬한다. ([Waikay](https://waikay.io/geo-action-plans/))
- Scrunch는 핵심 제품군과 연결된 고의도 질문, `high impact, low performance` 구간을 먼저 보도록 안내한다. ([Scrunch](https://scrunch.com/how-tos/how-to-identify-website-optimization-opportunities-for-ai-search/))
- Profound Projects는 매주 가시성·인용·프롬프트 격차를 분석해 왜 중요한지와 과제를 제안하지만 공개된 우선순위 산식은 없다. ([Profound Projects](https://help.tryprofound.com/articles/8581387448-about-projects?lang=en))
- Intercom의 RICE도 목표에 대한 영향, 근거 확신도, 노력을 함께 보며 점수를 절대 규칙으로 쓰지 말라고 설명한다. ([Intercom RICE](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/))

위 자료는 제품 운영 사례와 판단 구조의 참고 근거이며, 특정 우선순위 방식의 GEO 성과를 입증하는 인과 자료로 사용하지 않는다.
경쟁 제품이 영향도와 실행 용이성을 함께 사용한다는 사실은 두 축을 같은 무게로 합쳐야 한다는 근거도 아니다. 이 PRD는 고객·사업 영향을 제1원칙으로 두고 실행 효율은 같은 영향 등급의 보조 기준으로 제한한다.

#### 기존 결정과의 구분

- 결정 04의 `질문 우선순위`는 **무엇을 측정할지** 정한다.
- 결정 08의 `행동 우선순위`는 측정한 격차 중 **무엇을 먼저 바꿀지** 정한다.
- 사업 영향은 실제 매출 기여의 증명이 아니라 고객이 확정한 목표와 기대 행동에 비추어 본 **사업 기여 가능성**이다.

`고객·사업 영향`은 다음 두 요소로 설명한다.

- **고객 영향:** 미노출·추천 제외·잘못된 설명이 타깃 고객의 문제 해결과 구매 판단에 미치는 영향
- **고객사 사업 영향:** 브랜드 탐색·비교·체험·도입 검토 등 고객사가 등록한 기대 행동과 KPI에 미치는 영향

#### 전체 답안 반영

- `01`: 정확성 가드레일과 이후 행동 정렬 원칙을 명시한다.
- `02` FR-16: 관문·P0·영향 등급·신뢰도·실행 효율의 단계형 규칙을 적용한다.
- `02` FR-17: 사용자가 제안 순서와 변경 이유를 수정·기록할 수 있게 한다.
- 핵심 가치 지표는 `고객·사업 영향 근거가 연결된 1순위 행동 또는 검증 과제 확정률`로 정제한다.
- 리스크에는 자동 우선순위 오판과 고영향·저신뢰 행동의 검증 분기를 추가한다.

### 결정 09 — GEO 종합 점수의 비교 기준

- 상태: **확정**
- 선택: **C. 자사 절대 성과와 경쟁사 상대 성과를 함께 보는 이중 기준**

#### 사용자 선택

- 사용자는 추천안대로 절대·상대 이중 기준을 사용하기로 했다.
- 중대한 사실 오류는 높은 노출·추천 점수에 평균으로 묻히지 않도록 별도 품질 가드레일로 다룬다.

#### 답변 정제

1. **자사 절대 성과:** 고객이 확정한 목표 질문군에서의 가중 노출률·가중 추천률과 자사 추이
2. **경쟁사 상대 성과:** 같은 질문·모델·기간에서 고정 경쟁사군 대비 가중 추천 점유율을 점수화하고, 선두 격차·평균 추천순위는 진단으로 분리
3. **품질 가드레일:** 고객이 P0로 확인한 중대한 사실 오류 또는 실제 적합 조건과 어긋난 주의·비추천의 최신 상태가 `활성·해제 후보·재개방`이면 원시 지표와 원점수를 변경하지 않고 최종 등급을 `주의` 또는 `위험`으로 표시

`원자 지표 → 절대·상대 하위 점수 → 원점수·기본 등급 → 확인된 품질 가드레일 → 최종 등급`

- 자동 오류 후보는 확인 전까지 `검토 필요`로 표시할 뿐 점수를 제한하지 않는다.
- 감성은 추천이나 사실 정확성과 같지 않고 인용 수는 생성 원인의 증명이 아니므로 종합 점수에서 제외하고 진단 지표로 유지한다.
- MVP에서는 검증되지 않은 소수점 정밀도를 피한다. 정확한 가중치·등급 경계는 파일럿에서 보정하고 산식 버전을 기록한다.
- 종합 점수는 고객의 질문·경쟁사 범위 안에서만 유효하며 서로 다른 계정의 업계 순위를 뜻하지 않는다.

#### 조사·선택 검증

- Profound는 Visibility·Share of Voice·Positioning·Sentiment를 별도 지표로 제공하고 FactCheck도 독립 정확성 계층으로 운영한다. ([Profound](https://help.tryprofound.com/articles/3443229936-answer-engine-insights-overview), [FactCheck](https://help.tryprofound.com/articles/5793584301-about-factcheck))
- Scrunch도 brand presence, competitive presence, position, sentiment, citations를 나눠 보여주며 점유율 하나만으로 전체 성과를 설명하지 않는다. ([Scrunch](https://scrunch.com/how-tos/how-to-track-brand-presence-in-ai-search/))
- Peec는 Visibility와 Share of Voice를 별도 정의한다. ([Peec Visibility](https://docs.peec.ai/metrics/brand-metrics/visibility))
- Ahrefs는 AI Share of Voice가 설정한 자사·경쟁사 엔티티에 따라 크게 바뀔 수 있다고 명시한다. ([Ahrefs](https://help.ahrefs.com/en/articles/15501968-ai-visibility-metrics))

따라서 보편적으로 합의된 GEO 종합 점수는 확인되지 않았다. 이 구조는 시장 표준을 복제한 것이 아니라, 분리된 원자 지표를 고객의 의사결정에 맞게 압축하는 **MVP 제품 가설**이다. 품질 등급 상한 역시 경쟁 제품의 표준 관행으로 주장하지 않는다.

#### 비교 가능성 규칙

- 질문·가중치·경쟁사군·플랫폼·반복 규칙·산식·품질 등급 상한 규칙의 버전을 저장한다.
- 경쟁사군이 바뀌거나 표본이 부족하면 상대 성과의 시계열을 분리하고 `비교 불가`로 표시한다.
- 원점수·기본 등급과 품질 가드레일 적용 후 최종 등급, 적용 사유를 모두 보존한다.
- 경쟁사가 하락해 상대 성과만 좋아진 경우를 자사 개선으로 표현하지 않는다.
- 자사 절대 성과만 좋아졌지만 경쟁사보다 낮은 경우도 의미 있는 진전으로 별도 표시한다.

#### 전체 답안 반영

- `01` 기준 1을 자사 절대 성과와 경쟁사 상대 성과의 이중 기준으로 정제한다.
- `02` FR-08에 두 하위 점수·품질 등급 상한·원점수와 사유 공개를 반영한다.
- NFR에 경쟁사군·산식·품질 등급 상한 버전과 표본 부족·비교 불가 처리를 추가한다.
- 성공지표는 절대 성과 개선, 상대 성과 개선, P0의 현재 범위 내 미재현·운영상 해제를 분리한다. 해제 후 감시는 API의 4주 재개방률과 UI의 다음 유효 재검증 재개방률·30일 내 재관측 커버리지로 나눈다.
- 자사 절대 성과 70 : 경쟁 위치 30은 결정 10, 절대 성과 내부의 노출·추천 비중은 결정 11, 경쟁 위치의 가중 추천 점유율 단일 지표는 결정 12에서 확정했다. 등급 경계는 파일럿에서 보정한다.

### 결정 10 — 절대 성과와 경쟁사 상대 성과의 초기 가중치

- 상태: **확정**
- 선택: **B. 자사 절대 성과 70 : 경쟁사 상대 성과 30**

#### 사용자 선택

- 사용자는 추천안 B로 진행하기로 했다.
- 경쟁사보다 앞서는 것보다 고객이 선택한 중요한 질문에서 자사 성과가 실제로 나아지는 것을 우선한다.

#### 원점수 구조

`GEO 원점수 = 0.70 × 자사 절대 성과 + 0.30 × 경쟁사 상대 성과`

- **절대 성과 70:** 목표 질문군에서 자사의 가중 노출률·가중 추천률과 기준선 대비 추이
- **상대 성과 30:** 같은 질문·모델·기간·경쟁사군에서의 가중 추천 점유율. 선두 격차·평균 추천순위는 진단으로만 제공
- **품질 가드레일:** 100점 배분 밖에서 별도로 적용. 사람이 P0로 확인했고 최신 상태가 `활성·해제 후보·재개방`인 미해결 이슈가 있으면 원시 지표와 원점수는 보존하고 최종 등급을 `주의` 또는 `위험`으로 표시

#### 이 비율을 선택한 이유

1. 고객이 정한 문제와 목표 질문에서 성과를 내는 것이 제품의 제1가치다.
2. 경쟁사 상대값은 필요하지만 경쟁사 하락이나 경쟁사군 변경만으로도 움직일 수 있다.
3. 30%를 남겨 실제 후보군에서의 시장 위치를 무시하지 않는다.
4. 품질은 평균 가중치가 아니라 별도 가드레일이므로 70:30에 포함하지 않는다.

#### 해석 제한

- 70:30은 연구로 검증된 GEO 업계 표준이 아니라 사용자 가치관을 반영한 **MVP 제품 가설**이다.
- 파일럿에서는 사용자가 두 하위 점수와 종합 점수를 같은 방향으로 이해하는지, 상대 성과 변동이 전체 점수를 과도하게 흔들지 않는지 검증한다.
- 비율을 바꾸면 산식 버전을 올리고 이전 구간과 직접 비교하지 않는다.
- 절대 성과 내부의 노출률·추천률 비중은 결정 11, 상대 성과의 가중 추천 점유율 단일 지표는 결정 12에서 확정했다.

#### 전체 답안 반영

- `02` F1 구조와 FR-08에 70:30 원점수 산식을 명시한다.
- `README`와 내부 비교 문서에 고객 문제 우선의 MVP 가설임을 기록한다.
- 품질 등급 상한은 원점수 산식 밖에 유지한다.

### 결정 11 — 절대 성과 70점 안에서 노출과 추천의 비중

- 상태: **확정**
- 선택: **B. 가중 노출률 25 : 가중 추천률 45**

#### 사용자 선택

- 사용자는 추천 중심형 B로 진행하기로 했다.
- 중요한 질문에서 단순히 등장하는 것보다 실제 후보로 추천되는 것을 더 중요한 성과로 본다.

#### 절대 성과 산식

가중 노출률과 가중 추천률을 0~1로 정규화하면:

`자사 절대 성과 기여점수 = 25 × 가중 노출률 + 45 × 가중 추천률`

- 미노출은 두 지표 모두 0이다.
- `비교·검토 후보 / 단순 언급 / 주의·비추천`은 가중 노출률에는 포함하지만 가중 추천률에는 포함하지 않는다.
- `추천` 역할만 가중 추천률에 포함한다.
- 품질 가드레일은 이 70점 안에서 감점하지 않고 사람이 확인한 미해결 P0에 별도로 적용한다.

#### 선택 근거

1. 브랜드가 등장해야 추천될 기회가 생기므로 노출 25점을 남긴다.
2. 고객의 실제 질문은 단순 인지보다 후보 탐색·비교와 가까우므로 추천 45점을 더 크게 둔다.
3. 추천 역할 분류가 아직 시장의 공통 표준이 아니므로 추천에 55점 이상을 몰아 자동 판정 오류가 전체 점수를 지배하지 않게 한다.
4. `From Prompt to Purchase`는 추천 노출이 우연한 이름 언급보다 이후 브랜드 검색·사이트 방문과 더 크게 연관된다고 보고했다. 다만 거래를 관찰하지 못한 관찰 연구이므로 추천 가중치의 방향을 보조할 뿐 25:45를 증명하지는 않는다. ([arXiv 2606.10907](https://arxiv.org/abs/2606.10907))

#### 검증 조건

- 추천 판정에는 역할·근거 원문·신뢰도·사용자 수정 결과를 저장한다.
- 파일럿에서 역할 분류 정확도, 사용자의 판정 수정률, 노출과 추천 지표의 민감도를 확인한다.
- 비율 변경 시 산식 버전을 올리고 이전 점수와 직접 비교하지 않는다.

#### 전체 답안 반영

- `02` F1 구조·FR-08·우선순위 근거에 25:45를 명시한다.
- `03` 실측표에서 가중 노출률과 가중 추천률을 별도로 집계한다.
- `README`와 내부 비교 문서의 원점수 구조를 갱신한다.

### 결정 12 — 경쟁 위치 30점의 구성

- 상태: **확정**
- 선택: **A. 가중 추천 점유율 30점**

#### 사용자 선택

- 사용자는 경쟁 위치를 하나의 직접적인 상대 성과로 설명할 수 있는 A안을 선택했다.
- 선두 격차와 평균 추천순위는 버리지 않되 점수에는 넣지 않고 진단 정보로 사용한다.

#### 경쟁 위치 산식

`경쟁 위치 기여점수 = 30 × 가중 추천 점유율`

`가중 추천 점유율 = Σ(질문 가중치×자사 추천 사건) ÷ Σ(질문 가중치×자사·고정 경쟁사 전체 추천 사건)`

- 한 답변에서 여러 브랜드가 추천되면 브랜드별 추천 사건을 각각 센다.
- 자사와 고정 경쟁사 모두 추천되지 않은 답변은 상대 점유율의 분모에는 들어가지 않지만 절대 추천률에는 미추천으로 반영된다.
- 전체 추천 사건이 0이거나 표본 기준이 부족하면 0점으로 강제하지 않고 `비교 불가`로 표시한다.

#### 이 구성을 선택한 이유

1. 가중 추천 점유율은 동일 질문군에서 실제 추천 후보 자리를 얼마나 차지했는지 가장 직접적으로 설명한다.
2. 선두 격차는 `선두 점유율-자사 점유율`로 같은 데이터에서 파생되므로 함께 점수화하면 하나의 경쟁 신호를 이중 반영한다.
3. 평균 추천순위는 자사가 추천된 답변만 대상으로 하므로, 추천 빈도는 낮지만 드물게 1위인 브랜드를 과대평가할 수 있다.
4. 따라서 선두 격차와 평균 추천순위는 점유율 변화의 이유를 해석하되 종합 점수를 바꾸지 않는 진단으로 둔다.

#### 추가 조사와 선택 검증

- Scrunch는 Share of Voice와 평균 순위를 별도 지표로 제공한다. 평균 순위는 브랜드가 등장한 응답만 계산하고 미등장 응답은 제외하므로 presence와 함께 보라고 명시한다. ([Scrunch Query API](https://developers.scrunch.com/api-reference/query/overview))
- Profound도 Share of Voice와 Positioning을 구분해 제공한다. ([Profound](https://help.tryprofound.com/articles/3443229936-answer-engine-insights-overview))
- Ahrefs는 AI Share of Voice가 등록한 자사·경쟁사 엔티티 구성에 따라 크게 달라질 수 있다고 경고한다. 따라서 경쟁사군을 고정하고 버전을 저장해야 한다. ([Ahrefs](https://help.ahrefs.com/en/articles/15501968-ai-visibility-metrics))
- 공개된 상용 지표의 점유율은 주로 **언급** 기준이다. 이 결정의 **가중 추천 점유율**은 시장 표준을 그대로 쓴 것이 아니라, 추천을 단순 언급보다 중시하는 사용자 가치관을 반영한 MVP 제품 가설이다.

#### 해석 제한과 검증 조건

- 상대 점수는 고정한 질문·가중치·모델·기간·반복 규칙·경쟁사군 안에서만 비교한다.
- 경쟁사 추가·삭제 시 경쟁사군 버전을 올리고 이전 점수와 직접 비교하지 않는다.
- 상대 점유율이 올라도 자사 추천률이 그대로라면 자사 개선으로 표현하지 않는다.
- 파일럿에서는 추천 역할 분류 정확도, 경쟁사군 변화 민감도, 저표본 변동폭을 검증한다.

#### 전체 답안 반영

- `01`의 상대 성과는 가중 추천 점유율을 판단 지표로, 선두 격차·평균 추천순위는 진단으로 분리한다.
- `02`의 원점수를 `25×가중 노출률 + 45×가중 추천률 + 30×가중 추천 점유율`로 확정한다.
- `03`의 실측 집계에서 질문 중요도를 반영한 추천 점유율과 경쟁 위치 30점 기여분을 계산한다.
- `README`와 내부 비교 문서에 동일 구조를 반영한다.

### 결정 13 — 확인된 P0 품질 가드레일의 적용 방식

- 상태: **확정**
- 선택: **B. 원점수는 보존하고 최종 등급만 제한**

#### 사용자 선택

- 사용자는 추천안대로 중대한 품질 문제를 숫자 감점으로 섞지 않고 최종 등급 상한으로 처리하기로 했다.
- 높은 노출·추천 성과와 중대한 사실 오류가 동시에 존재할 수 있으므로 두 사실을 모두 보존해야 한다.

#### 표시 구조

```text
GEO 원점수       84 / 100
기본 등급        양호
품질 가드레일    적용
최종 등급        주의
사유              핵심 구매 질문에서 보안 인증 정보를 사실과 다르게 설명
```

- P0가 있어도 원시 지표·원점수·기본 등급은 바꾸지 않는다.
- 최종 등급을 `주의` 또는 `위험`으로 표시하고 P0 원문·승인된 기준 정보·사용자 확인자·확인 시각을 함께 표시한다.
- 등급 순서는 `양호 > 주의 > 위험`으로 두고, 최종 등급은 원점수 기반 등급과 `주의` 중 더 낮은 등급으로 정한다. 원점수 기반 등급이 이미 위험이면 주의로 올라가지 않는다.
- 자동 오류 후보는 `검토 필요`일 뿐 가드레일을 적용하지 않는다. 승인된 기준 정보와 근거 원문을 사람이 대조해 P0로 확정한 경우에만 적용한다.
- 정확한 등급 경계와 반복 P0의 추가 하향 규칙은 별도 결정·파일럿 검증 대상으로 남긴다.

#### 이 방식을 선택한 이유

1. 원점수는 정해진 질문군에서 관측한 양적 성과이므로 품질 사건 때문에 다시 쓰면 지표의 의미와 추이가 훼손된다.
2. 반대로 경고 배지만 붙이면 높은 점수만 보고 중대한 오류를 놓칠 수 있다.
3. 숫자 상한은 근거 없는 특정 점수로 과대정밀성을 만들지만 등급 상한은 ‘현재 양호하다고 판단할 수 없다’는 의사결정 규칙을 직접 전달한다.
4. 원점수·기본 등급·최종 등급·사유를 함께 공개하면 경영진 요약과 실무자 검증을 동시에 지원한다.

#### 추가 조사와 선택 검증

- Profound FactCheck는 정확성을 가시성과 분리한 계층으로 운영하고, 브랜드 기준 정보와 원자적 사실 주장을 대조하며 사용자가 오탐을 제거할 수 있게 한다. 이는 정확성을 별도 품질 계층으로 두고 기준 정보·사용자 확인을 요구하는 설계를 뒷받침한다. 다만 최종 등급 상한을 사용한다는 공개 근거는 확인되지 않았다. ([Profound FactCheck](https://help.tryprofound.com/articles/5793584301-about-factcheck))
- NIST AI RMF는 위험 허용 수준이 맥락별로 정의되어야 하고, 높은 위험은 평균적인 이익과 별개로 우선 관리해야 한다는 원칙을 제시한다. 이는 중대 위험을 평균 점수에 묻지 않는 일반 원칙의 근거이지 GEO 전용 등급 산식의 근거는 아니다. ([NIST AI RMF](https://airc.nist.gov/airmf-resources/airmf/1-sec-risk/))
- 따라서 `주의` 또는 `위험` 등급 표시는 시장 표준을 복제한 것이 아니라, 중대한 고객 오판 위험을 높은 노출 성과와 분리해 전달하는 MVP 제품 가설이다.

#### 적용과 해제 원칙

- `검토 필요 → 사용자 확인 → P0 활성 → 수정·대응 → 즉시 동조건 검증 → 해제 후보 → 사용자 해제 → 경로별 지속 감시` 상태를 기록한다. 공식 API는 주간, UI는 결정 16의 월간+이벤트 트리거 주기를 따른다.
- 미해결 P0가 하나라도 남아 있으면 최종 등급 상한을 유지한다.
- 동일 사실 문제는 하나의 `issue_family_id`로 묶고, 경로별 `issue_id` 아래 반복·다중 모델 관측과 최초/최근 시각을 합친다. 반복 관측은 P0 개수를 부풀리거나 숫자를 추가 감점하는 대신 재현성과 영향 범위를 설명한다. 이 경로별 상태 구조는 결정 15에서 정제했다.
- 오탐은 사용자가 기각하면 근거와 확인자를 남기고 해제한다. 실제 오류는 당시 영향받은 모든 질문–모델 조합×반복의 즉시 검증 사이클을 누락·실패 없이 마쳐 미재현되고 사용자가 최신 기준 정보와 원문을 다시 확인해야 해제한다. 이후 API 주간 측정 또는 다음 유효 UI 표본에서 재발 후보를 사람이 확인하면 같은 경로별 `issue_id`를 재개방한다.
- 모델 버전 변경 등으로 직접 비교할 수 없으면 자동 해제하지 않고 이슈 상태를 유지한 채 검증 결과를 `재검증 필요`로 표시한다. 해제 후 같은 이슈가 다시 나타나면 사람 확인을 거쳐 기존 `issue_id`를 재개방한다.
- 가드레일 규칙이 바뀌면 버전을 올리고 과거 최종 등급과 구분한다.

### 결정 14 — P0 등급 상한 해제와 이후 감시 방식

- 상태: **확정**
- 선택: **즉시 1회 검증 사이클 + 이후 주간 측정의 혼합형**
- 성격: **외부 표준이 아니라 파일럿에서 해제 후 재개방률로 검증할 MVP 운영 가설**

#### 사용자 답변과 정제

- 사용자는 1회 측정과 주간 측정을 함께 사용하고, 첫 측정 뒤의 변화도 계속 측정해야 한다고 판단했다.
- 여기서 `1회 측정`은 답변 한 번이 아니라, 수정 직후 영향받은 모든 질문–모델 조합을 같은 조건에서 설정 횟수만큼 반복하고 누락·실패 없이 완주하는 **한 번의 유효한 측정 사이클**로 정제한다.
- 즉시 사이클은 빠른 변화 확인과 등급 상한 해제 판단에, 주간 측정은 변화 유지·추세·재발 감시에 사용한다.

#### 확정 흐름

```text
P0 확인·활성
→ 수정·대응 완료
→ 영향받은 모든 질문–모델 조합×경로별 선언 반복 즉시 검증(API 최소 3회, UI 반복 수는 후속 결정; 누락·실패 없음)
→ 기준선 대비 변화와 전 반복 오류 미재현 확인·해제 후보 전환
→ 사용자 재확인·이슈 해제
→ 계정의 활성·해제 후보·재개방 P0 0건이면 등급 상한 해제
→ 공식 API 전체 목표 질문군 주간 측정 + 다음 유효 통제 UI 표본
→ 유지면 추세 누적 / 재발 후보는 사람 확인 후 같은 issue_id 재개방
```

#### 적용 규칙

- 즉시 검증은 P0 확인 당시와 같은 `measurement_route`·제품 표면·질문 버전·언어·지역·모델 ID(또는 UI 표시 모델)·검색 도구/설정 버전·반복 규칙을 사용한다. 영향받은 모든 질문–모델 조합×설정 반복을 누락·실패 없이 완료해야 유효 사이클로 인정한다. `search_used`는 고정 조건이 아니라 실행 결과이므로 일치 요건으로 삼지 않고 매 실행 기록한다.
- 전 조합·전 반복에서 오류가 미재현되고 사용자가 최신 기준 정보와 원문을 다시 확인·승인해야 해당 이슈를 해제한다. 브랜드 자체가 나타나지 않은 응답은 `정정 성공`이 아니라 `미등장으로 미재현`으로 구분한다.
- 계정의 `활성 / 해제 후보 / 재개방` P0가 모두 0건이어야 최종 등급 상한을 해제한다. 다른 미해결 P0가 있으면 개별 이슈 해제와 무관하게 계정 상한은 유지한다.
- 즉시 검증은 `기준선 대비 변화`를 보여주되 문제의 영구 소멸이나 우리 행동의 인과 효과로 단정하지 않는다. 해제는 `현재 비교 가능한 범위에서 미재현되어 운영상 해제`라는 의미다.
- 공식 API 주간 측정에서는 즉시 검증 결과와 전주 대비 추이를 함께 보여준다. UI는 다음 유효 통제 표본에서 같은 오류의 재발 후보를 확인한다. 어느 경로든 사람이 확인한 경우에만 해당 경로의 기존 `issue_id`를 재개방하고 상한을 다시 적용한다.
- 모델 버전·측정 경로·제품 표면·검색 설정 버전 중 하나라도 바뀌면 이슈 상태는 유지하고 검증 결과만 `비교 불가 / 재검증 필요`로 표시하며 성과 변화로 합치지 않는다.
- 비교 기준 사이클·조건 버전·`measurement_route`·제품 표면·`search_policy`·`search_used`·영향 범위·완주 여부·검증 결과와 해제/재개방 승인자·시각을 기록한다. API는 `해제 후 4주 내 동일 이슈 재개방률`, UI는 `다음 유효 재검증 시 재개방률`과 `30일 내 재관측 커버리지`를 본다.

#### 선택 근거와 한계

1. 수정 결과를 확인하기 위해 다음 정기 측정까지 기다리게 하면 고객의 행동–학습 주기가 느려진다.
2. 즉시 검증만으로 끝내면 생성 변동 때문에 우연한 미재현을 해결로 오해할 수 있다. API 주간 감시와 UI 월간·이벤트 트리거 재검증이 이를 보완한다.
3. 전체 질문군을 즉시 다시 돌리지 않고 영향받은 질문–모델만 실행해 호출 비용을 제한한다.
4. Profound FactCheck가 기간별 정확도 변화를 제공하고, NIST AI RMF가 지속적·정기적 모니터링을 권고하는 것은 재검증과 지속 감시 방향을 뒷받침한다. 다만 `한 유효 사이클 후 사람 승인으로 운영상 해제`, `API 주간 감시`, `UI 후속 표본`이라는 구체 규칙은 외부 표준이 아니라 MVP 운영 가설이다. 파일럿에서는 API 4주 재개방률과 UI 재관측 커버리지를 분리해 검증한다. ([Profound FactCheck](https://help.tryprofound.com/articles/5793584301-about-factcheck), [NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/))

### 결정 15 — 측정 정본과 웹 UI의 역할

- 상태: **확정**
- 사용자 선택: **C — API 공식 시계열 + 개인화 요인을 줄인 웹 UI 표본 점검의 혼합형**
- 핵심 원칙: **역할을 분리하고 두 경로의 점수를 합산하지 않는다.**

#### 사용자 답변과 정제

- 사용자 답변: “혼합형으로 해.”
- API는 모델·검색·언어·지역 등 기록 가능한 조건을 고정해 주간 전체 측정과 조치 직후 검증에 쓰는 **공식 시계열**이다.
- 웹 UI는 고객이 접하는 제품 경험과 API 추세의 차이를 찾는 **통제 대표성 표본**이다. 로그아웃·시크릿이어도 IP/네트워크 위치가 남을 수 있으므로 `비개인화`라고 약속하지 않는다.
- 확인한 공식 문서에는 API와 소비자 UI의 응답 동일성 보장이 없으므로, API 값을 실제 소비자 전체 노출의 대리값으로 단정하거나 두 경로를 평균내지 않는다.

#### 확정 구조

| 경로 | 용도 | 필수 기록 |
|---|---|---|
| **API** | 주간 공식 시계열·조치 직후 동일 조건 검증 | 사업자·API 표면·모델 ID·질문/조건 버전·언어·지역·`search_policy`·`search_used`·반복·시각 |
| **웹 UI** | API 추세의 대표성 차이와 실제 제품 경험 표본 점검 | 계정/로그인 상태·Memory/프로필/Connected Apps·요금제·표시 모델·검색 모드·네트워크 지역·질문 버전·시각 |

- OpenAI Responses API와 Gemini처럼 검색 실행 여부를 모델이 판단하는 경로는 검색 호출 블록·UI 검색 표시·인용 등 실행 증거로 `search_used`를 기록하고, 확인할 수 없으면 `unknown`으로 둔다. Perplexity Sonar처럼 웹 그라운딩을 전제로 한 경로도 실제 검색 결과·인용 메타데이터를 기록한다.
- UI 자동화는 별도 허용이 확인되기 전 수동 또는 사용자 보조 표본으로 제한하고, 반복 가능한 공식 측정은 API를 사용한다.

#### P0 origin-route 규칙

1. P0에는 `issue_origin_route`·`issue_origin_cycle_id`·`issue_confirmed_scope_pairs`를 확정 시점에 저장한다. 한 경로에서 사람 확인된 P0도 계정 등급 상한은 작동시키되, 다른 경로의 원점수·관측 사실을 덮어쓰지 않는다.
2. 같은 사실 오류가 양쪽에서 확인되면 `issue_family_id`로 한 문제처럼 연결하되, API·UI에는 경로별 `issue_id`와 상태를 둔다. API 발생이 UI 발생을 증명하지 않고, UI 발생도 API 시계열 원점수를 바꾸지 않는다.
3. 해제 검증은 **각 `issue_id`의 원발생 사이클을 비교 기준으로 삼아, 원발생 경로·확정 영향 범위·같은 조건 버전**에서 수행한다. 즉시 검증 전 행에 `verification_issue_id`와 `통과 / 미등장으로 미재현`을 기록하고 사람이 승인해야 한다. 한 경로의 미재현이나 다른 범위의 성공으로 다른 경로의 레코드를 해제하지 않는다.
4. 모델·경로·제품 표면·검색 설정이 달라지면 `비교 불가 / 재검증 필요`이며 변화량에 합치지 않는다.

#### 검증 근거

- OpenAI·Anthropic·Gemini의 API 검색 도구는 검색 설정과 실제 사용이 구분되고, 각 소비자 UI에는 위치·개인화·모델/검색 설정이 별도로 존재한다. Perplexity도 API가 공개 답변 엔진과 같은 검색 인프라를 쓴다고 설명하지만, 확인한 문서에는 출력 동일성 보장이 없다.
- 공식 약관상 UI 대량 자동화는 금지되거나 허용 범위가 불명확하므로 API 자동화와 수동 UI 표본을 분리한다.
- 출처: [OpenAI API Web Search](https://developers.openai.com/api/docs/guides/tools-web-search) · [ChatGPT Search](https://help.openai.com/en/articles/9237897-chatgpt-search) · [Claude API Web Search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) · [Claude UI 검색](https://support.claude.com/en/articles/10684626-enable-and-use-web-search) · [Gemini API Google Search](https://ai.google.dev/gemini-api/docs/google-search) · [Gemini UI 위치](https://support.google.com/gemini/answer/13275745?hl=en-GB) · [Perplexity Sonar API](https://docs.perplexity.ai/docs/sonar/quickstart) · [Perplexity UI 설정](https://www.perplexity.ai/help-center/en/articles/10352990-account-settings)

#### 미결

- 당시 웹 UI 표본의 **질문 수·반복 수·모델/요금제 구성**은 미결이었고, 이후 결정 17에서 질문 6개×UI 3종×2회=월 36회로 확정했다.
- UI의 정확한 모델 빌드·시스템 지침·검색 랭킹은 공개 정보만으로 확인할 수 없다. 표시 모델명은 저장하되 API 모델과 동일하다고 판정하지 않는다.

#### 전체 답안 반영

- `01`에는 좋은 GEO의 재현성 조건을 경로·검색 설정까지 확장한다.
- `02`에는 API 공식 시계열/UI 통제 표본 분리, 합산 금지, `search_used`, P0 경로별 해제 규칙을 반영한다.

### 결정 16 — 통제 UI 대표성 표본의 운영 주기

- 상태: **확정**
- 사용자 선택: **C — 월 1회 정기 표본 + 이상 징후 발생 시 추가 실행**
- 성격: **외부 표준이 아니라 비용·탐지력·오경보를 파일럿에서 검증할 MVP 운영 가설**

#### 사용자 답변과 정제

- 사용자 답변: “C로 하고.”
- 신규 계정에는 최초 통제 UI 기준 표본을 한 번 만들고, 이후 월 1회 같은 범위의 대표성 표본을 실행한다.
- 다음 사건은 월간 주기를 기다리지 않는 추가 실행 트리거다.
  1. 동일 조건 API 가중 노출률·추천률이 축적된 변동 범위를 벗어남
  2. 제공사가 소비자 UI·표시 모델·검색 모드 또는 주요 개인화 설정을 변경함
  3. 고객이 실제 UI 답변의 미노출·잘못된 추천·사실 오류를 제보함
  4. 어느 경로에서든 사람이 P0를 확정해 실제 화면 영향 확인이 필요함

API 이상 임계값은 근거 없는 고정 %로 두지 않고 초기 기준선의 회차·주간 변동이 쌓인 뒤 정한다. 모든 UI 사이클에는 `initial / monthly / api_anomaly / provider_change / customer_report / p0_event / p0_verification` 중 실행 계기를 기록한다.

#### 이 방식을 선택한 이유

1. UI는 공식 시계열이 아니라 대표성 검증이므로 매주 전체 반복하면 API와 역할이 중복되고 수동 운영 비용이 커진다.
2. 월 1회만 실행하면 제공사 변경이나 고객 피해 신호를 다음 정기일까지 놓칠 수 있다.
3. 월간 기준 표본으로 장기 괴리를 보고, 사건 기반 추가 표본으로 고위험 변화에 빠르게 대응하면 안정성과 민감도를 함께 확보할 수 있다.
4. UI 표본은 API 점수에 합산하지 않으며, 이벤트 표본이 많아져도 공식 성과가 좋아지거나 나빠지는 것으로 계산하지 않는다.

#### 성공·감사 기준

- 월간·이벤트 UI 표본의 선언 범위 완주율과 실행 계기별 탐지 건수·오경보·수동 소요 시간을 기록한다.
- UI P0는 해제 후 30일 안에 같은 범위를 한 번 이상 재관측했는지와 다음 유효 UI 표본의 재개방률을 함께 본다. 미관측은 `재발 없음`으로 세지 않는다.
- 제공사 변경이나 API 이상이 실제 UI 괴리로 이어지지 않은 경우도 기록해 트리거의 유용성을 파일럿에서 보정한다.

#### 남은 결정

- UI 표본의 질문 수·질문 선정 규칙·반복 수·모델/요금제 구성은 이후 결정 17에서 확정했다.
- 최종 제출 PDF의 목표 장수·편집 밀도는 내용 확정 후 결정한다.

## 4. 남은 결정 일괄 위임

사용자는 “이제 얼추 내 가치관과 너의 대답이 맞아떨어지니 전체 너 추천대로 가주는데 예정 질문과 선택지, 답변은 이력으로 남겨줘”라고 답했다. 따라서 결정 17~23은 사용자가 각 선택지를 직접 고른 것으로 기록하지 않고, 앞선 대화에서 확인한 가치관과 제출 조건에 따라 **추천안에 결정을 위임한 것**으로 기록한다.

적용 기준은 다음과 같다.

1. 기술 설명보다 고객이 해결하려는 문제와 기대 결과를 먼저 본다.
2. 고객 문제에서 목표 질문을 만들고, 측정 결과를 다음 행동과 재측정으로 연결한다.
3. 공식 성과와 실제 UI 대표성 표본을 섞지 않는다.
4. 근거 없는 정밀도보다 설명 가능하고 반복 가능한 최소 설계를 우선한다.
5. 2026년 8월 17일 제출 기한 안에서 직접 검수하고 면접에서 방어할 수 있는 범위로 제한한다.
